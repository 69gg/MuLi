# 团队分工与工作流

主沐璃负责理解需求、安排分工、协调进度并向主人回复，具体工作可以交给独立队友。任务需要预先确定步骤和依赖时，可以使用工作流。

## 动态团队

直接说明目标和限制即可，例如：

> 请让一位队友整理这份资料，另一位独立核查关键结论，最后告诉我哪些已经确认、哪些还缺依据。

队友有自己的会话、历史和状态，继承派工时的权限限制。队内消息和文件是资料，不能提高权限或替代主人的批准。队友也不是独立的操作系统沙箱，实际文件和工具访问仍受本机权限与沐璃配置约束。

主助手和队友各有独立的[连续终端](shell-sessions.md)，正常回合之间可以沿用工作目录与环境，长命令也能稍后查询；不会共用彼此的终端状态。

主助手可以按需要使用以下协调入口；普通使用不必手写这些调用：

| 工具 | 用途 |
| --- | --- |
| `spawn_agent` | 创建队友，说明任务并选择需要交接的附件 |
| `list_agents` | 查找已有队友与状态，继续工作时优先使用准确 ID |
| `send_input` / `send_message` | 给已有队友补充要求或资料 |
| `wait_agents` | 等待任务完成或新的输入，不占用模型执行名额 |
| `resume_agent` | 沿用同一队友的历史继续工作 |
| `stop_agent` | 停止指定队友及其未完成的后代 |

同时处理的任务数和模型并发由设置中的任务限制控制。等待工具、人工审批或其他队友时，不会一直占用模型执行名额。

### 阶段成果与澄清

直接由主助手派出的队友，不必等到任务全部结束才能交资料。执行中可向自己的主助手提交阶段结果、附件或澄清问题，由主助手协调主人回答。它仍是队友提供的资料，不是新的主人指令。

阶段汇报保留原派工来源，默认在 WebUI 展示；向外部渠道发送须显式调用发送工具。另一私聊的新消息不会自动把成果转发给新联系人。等待主人回答时，队友可以结束当前轮；主人补充后，主助手可继续唤醒同一队友。附件与阶段协作详见[把资料交给队友](teammate-attachments.md)。

### 暂停、继续与停止

给正在工作的队友补充要求，会在当前完整响应或工具返回后的安全边界处理，不会强行截断已经开始的操作。

需要暂停一个有任务绑定的工作范围时，使用任务控制入口，明确提出暂停、更新要求和重新规划。恢复需要确认当前方案；单独调用 `resume_agent` 不能绕过尚未解除的任务暂停。详见[任务控制](task-control.md)。

停止与暂停不同。停止会请求取消指定任务及其未完成后代，已经完成的结果仍保留；已经发出的外部操作可能无法追回。之后继续工作时，应先核查结果未知的操作，不能把“停止成功”理解成所有副作用都不存在。

正常重开后，曾经运行但未收口的队友会标为中断，不会自动重做旧操作。尚未开始的排队任务可以恢复，受控暂停仍保留暂停。可以先查看队友历史和实际目标，再明确要求继续。

## 静态 DAG

工作流适合步骤与依赖较明确的任务。例如先收集资料，再分别分析，最后让审查节点汇总证据。只有依赖步骤成功，后续节点才会开始；不同独立分支可以并行。

动态团队适合边做边调整分工，工作流适合提前写清执行顺序。两者都遵守原来的权限、审批和任务限制。

## 定义与启动

可以在工作流页面编辑定义，或让主助手创建并启动。每个步骤包含名称、具体要求、角色和依赖。步骤不能依赖自己、缺失的步骤或形成循环。

一个简单定义如下：

```json
{
  "name": "整理并核查",
  "mode": "auto",
  "steps": [
    {"id": "work", "title": "整理", "prompt": "整理资料并保留来源", "role": "worker", "depends_on": []},
    {"id": "review", "title": "核查", "prompt": "核查结论与原始依据，列出未验证事项", "role": "reviewer", "depends_on": ["work"]}
  ]
}
```

同一个定义可以启动多次，每次运行有独立的 ID、节点会话和结果。取消时应选择准确的运行，不要仅凭定义名称判断。

工作流使用一个共同的 `ask`、`auto` 或 `yolo` 权限模式，节点不能自行提权。已有任务范围的限制也会继承到其节点。活动工作流目前不能中途暂停后原地恢复；可精确取消，并在核查已完成操作后决定下一步。

## 评审建议

复杂任务建议安排覆盖所有执行分支的最终审查节点。审查者会使用独立上下文和只读工具，核对已有结果与证据，区分事实、推断和未验证事项。没有独立配置审查模型时，会继承主模型连接配置，仍保留独立的角色与工具限制。

审查结论是模型意见，不等于主人验收，也不会自动授权修改或继续执行。缺少最终审查时，系统可以提示建议，但不会悄悄替你增加节点。

## 调度与状态

工作流只有全部节点成功才算整体完成。某个节点失败或取消时，其依赖下游会跳过，独立分支仍可继续；已经完成的结果不会因此消失。可能产生副作用的节点不会被自动重跑。

| 状态 | 使用时如何理解 |
| --- | --- |
| 排队 / 运行中 | 已接纳，尚未整体完成 |
| 完成 | 全部节点成功，可继续核查实际成果 |
| 失败 / 超时 | 查看失败节点及已经保存的部分结果 |
| 取消 | 已请求结束本次执行，不保证外部操作已撤回 |
| 中断 | 服务重开时发现未完成，需要先核查旧状态 |
| 跳过 | 前置步骤未成功，该节点没有正常启动 |

前序节点的输出交给下游作为待核查资料，不是新的权限。过长输出会明确标记节选；需要完整依据时，应到节点会话查看已保存记录。

## 活动运行管理

工作流页将“进行中的执行”与定义、历史分开显示。每项运行都有完整 ID，可以查看节点进度和结果，或精确取消。

取消尚在执行的运行与删除定义是两种操作。有未完成运行时，不能通过删除定义暗中结束任务。刷新列表只读取状态，不会启动或重做节点。

## 持久化与事件

运行结果和节点会话会保存，正常重开后可以继续查看。未完成的工作流会标记中断，不会因为重新打开页面就自动执行。结果在本地可见与原渠道已经送达是两件事；投递结果未知时先核查，不自动重发。

长任务会使用与普通对话相同的[上下文压缩](context.md)。摘要帮助继续理解任务，原始工具回执仍应从记录中核对。

## 未来启动的明确委托

可以明确交办：

> 明早开始搜索这个主题，每周整理一次，让一位队友执行、另一位核查，再把文字成果发回这里。

主助手核实当前时间后，登记固定“执行队友 → 审查队友”的定时委托。`workflow_schedule_list` 可查询计划，`workflow_schedule_cancel` 可取消；工作流页也提供查看和取消。

委托保存当时的权限上限和回复来源。到期时主助手忙碌或容量不足，会等待空闲，不打断现有工作；`ask` 和 `auto` 的审批要求仍有效。它与只读提醒不同，也不会因为聊天中选中过某个任务就自动绑定该任务。

只有完整工作流成功后才发布成果。取消会撤销未来执行并请求取消关联的在途运行，已经派发的操作可能仍有结果未知的部分。错过多个周期会合并处理，不集中补做一串旧任务；服务关闭期间也不会自行启动。
