# 主沐璃的系统注意事项

`AttentionInbox` 把明确的本机接收事实、维护与提醒事件交给唯一主会话处理。它等待 SQLite 事件总线的变化，不定时询问模型；普通消息、工具结果、渠道输入与助手自己创建的通知不会自行触发它。chiliarch 普通消息另有默认关闭的本地策略，开启后只把新消息作为外部资料提醒。关闭网页不影响后台进程中的消费；进程未运行时不会唤醒电脑。

配置位于 `attention`，默认值如下。只有在出现已启用的合格事件、主模型已配置时，才会发起正常的主会话模型请求；因此开启注意事项可能产生事件触发的模型费用。Linux 桌面弹窗的 `notifications.enabled` 是独立设置。

```json
{
  "enabled": true,
  "events": ["reminder", "management", "update"],
  "batch_size": 8,
  "max_chars": 4000,
  "coalesce_seconds": 0.25
}
```

`events` 只能选择上述三类，不能填任意总线事件名。日志由独立的 `system_events.notify_enabled` 与级别策略控制，见[系统日志事件](system-events.md)；chiliarch 普通消息由[独立本地策略](chiliarch.md#普通消息提醒默认关闭)控制，主配置不增字段。`events=[]` 只停止上述三类新事项。要关闭全部注意事项并取消旧的待处理批次，使用 `attention.enabled=false`。`batch_size` 限制每次读取的事件条数，`max_chars` 限制一条系统输入的正文，实际正文还按当前上下文预算收紧。`coalesce_seconds` 只在发现合格事件后短暂等待合并突发事件，空闲没有计时轮询。主队列沿用 `limits.max_pending_runs`，其中最多保留一批尚未消费的注意事项，避免后台资料淹没前台输入。单个记录太长时保留事件 ID 和原记录 ID，并明确标注资料节选。

允许的来源与证据：

| 策略类别 | 总线事件 | 必须同时存在的持久证据 |
| --- | --- | --- |
| `reminder` | `notification.created`，`source=reminder` | 相同通知正文及来源、已触发的 reminder、对应通知 ID |
| `update` | `notification.created`，`source=update` | 相同通知正文及来源、当前已检查且确有新版的 update 记录、对应版本通知 ID |
| `management` | `management.completed` | 相同管理计划 ID、action、路由与终态；接受 configure/restart/update/adopt/switch 的 completed/failed；候选更新另接受精确 interrupted/candidate_cleaned |
| `management` | `management.progress` | 当前计划与事件均为 switch/update、applying/candidate_cleanup_required，且原路由一致；同一计划同一阶段去重 |
| 独立日志策略 | `system.log` | 当前 `system_log` 原记录、精确事件 ID、固定字段一致，且来源允许通知、级别符合策略 |
| 独立 chiliarch 策略 | `notification.created`，`producer=chiliarch_message` | 当前身份与 revision、原 inbox 正文的有限前缀及长度、canonical 通知的宿主证明与冻结路由均一致；仅两类普通消息 |

仅伪造一个同名事件不够。消费器回查 SQLite 的通知、提醒、版本和管理记录；管理计划的原始错误、配置快照、结果对象不进入模型，避免诊断中的凭据外泄。候选清理结束表示更新已中断，不表示安装或切换成功；其他 progress 与历史 interrupted 忽略，详情见[候选更新](candidate-host-design.md)。本地 Python 插件仍是用户信任的代码，能修改数据库与事件总线；这里不是针对恶意插件的操作系统沙箱。

chiliarch 的本地持久接收事实可信，正文仍是不可信外部资料，来源节选会明确标注。coalesce、等待空闲与等待配置锁之后，在入队事务前按每条来源证明再次核对当前身份和策略 revision；失效资料被下一次有界消费跳过，不使同批有效 reminder 卡住。未接纳旧消息不会因重配或重新启用获得新身份的授权；已接纳事项保留原历史身份，不承诺撤销所有既有批次。

系统资料不代表用户授权。每批输入固定使用 `source=principal=system:attention`、`route=null`，不执行 owner 消息 hooks，也不会自动提炼成用户身份记忆。为复用现有工具配对与多协议回放，历史使用 `user` 消息容器，但正文明确以“系统注意事项／非用户消息或新授权”开头；界面应根据 `principal` 标记为系统资料，不能显示成用户主动发言。内部 `Runtime.submit_attention()` 没有对应的公共 HTTP 入站入口；它在配置锁内再次检查执行任务、团队/工作流状态、待投递团队报告与主队列中的非注意事项输入。尚有这些工作时返回 `None` 表示延后，不写入 ingress、游标或去重凭据。

有活动主任务、队友或工作流时，收件箱等待它们实际结束及团队报告交接，再把资料交给独立的主会话回合；不会在工具批次之间插入提醒、中断流式，或跳过原任务尚未开始的已授权工具。主助手先回复、队友仍执行时也继续等待，直到队友结果回主会话并完成后续协调。队友终态与待投递报告原子提交，报告进入父会话队列后同步唤醒任务，避免这两次交接之间插入系统资料。离线恢复的 owner/agent 待处理输入也优先消费。原始通知仍可立即在工作台查看，模型说明会延后。

等待结束后若另一个 owner 任务、团队或工作流先启动，配置锁内的复核会再次延后交付。消费器优先等待实际主任务，否则等待实际队友或工作流节点任务；只有排队工作或待投递报告而没有运行时任务时，等待总线变化，不定时重试。

最新有效主输入是注意事项时，该次模型请求只开放 `risk=read` 的工具，不能通过注意事项启动团队、工作流、写业务文件、改配置或更新。宿主仍会保存工具结果及受限派生证据（例如 ASR 的私有转写工件），这不授予任意路径写入或外发权限。只读工具仍经过当前 ask/auto/yolo 权限检查；即使模型自行返回未提供的写工具调用，也会被执行边界拒绝。用户下一次真实 owner 输入恢复正常协调能力；注意事项不会继承历史 owner 的操作授权。

每次模型请求在上下文钩子首次 await 前冻结回复路由和事项分类。新提醒与管理计划、主会话当前请求失败继承宿主捕获的原始请求来源，WebUI 来源明确本地；旧记录、未准备请求的失败和其它日志留 WebUI。启动时自主更新检查、扩展目录自主 watch 的新失败状态，以及明确开启的 chiliarch 普通消息提醒登记为 independent，在通知/日志首次持久产生时选择 `channels.proactive` 的有效显式记忆绑定或普通默认，默认仍 WebUI；不是在消费事件或模型运行时重新选择。手动扩展重载即使由 watch 执行也不能自称独立。配置、平台权限和暂停规则见[默认通知](channels.md#无发令会话时的默认通知)。没有来源不代表独立；不依据自由记忆推断地址，也没有新增 WebUI 管理提交或手动更新检查入口。

同目的地的独立事项还须有相同选路依据才可合批：普通默认与记忆绑定分开，不同事实、版本、来源 ID 或摘要也分开。主身份与任务权限仍由既有 principal/TaskSnapshot 管理；选路元数据不进入模型资料正文。记忆失效仅使未来事项选普通默认，已冻结依赖项在入队及每段发送前复核并持久 blocked，不改原收件人、不复位 unknown。

Attention 只合并连续同一完整目的地与授权类型的事项，bound 和 independent 即使同发 A 也不混批。`routing` 小型元数据随 receipt/ingress/消息保存，资料正文不含它；principal 与授权守卫保持独立。旧 owner 的目的地不会被无来源事项借用；独立外发也不赋予系统资料新的写入、配置或发送工具权限。工具读取过程继续流式显示，只有完整无工具调用的最终答复可入渠道 outbox。默认 A 改 B 只影响新事项，撤销则 blocked，不改旧项地址，不自动重试 unknown。

持久状态、恢复与取消：

- `attention_state/cursor` 保存事件游标；`attention_receipt` 保存逻辑通知/计划终态的去重凭据、事件引用和冻结 routing。accepted 只说明系统输入已入队，不说明模型或渠道发送成功。批次通过 `Conversation.enqueue(objects=...)` 在同一 SQLite 事务提交 ingress、游标和凭据。提醒触发、首次更新通知、管理计划终态，以及模型消息各自与对应事件同事务保存，再唤醒消费者；中途失败全部回滚，不用启动扫描补洞。入队完成后进程退出也不会重复交付同一记录。
- 首次构造时从当前事件尾部开始，默认不补发此前历史；已存在的游标在进程恢复时继续消费。重新启用时跳过停用期间历史。需回看旧事项可访问原通知/管理记录。
- 未配置主模型时仍可持久排入一批；其余事件留在原事件日志。不会创建模型客户端或不断重试。应用在后续热配置后启动收件箱时，先恢复主队列，再继续消费。
- 等待活动执行或报告交接期间，尚未交付事件保留在原事件日志，游标不会越过它们。消费者使用 `asyncio.shield()` 等待实际任务，因此关闭或重配收件箱不会取消 owner 或队友的工作；重新启动后会重新核对策略与事件。
- 队列满时游标不越过未交付事件，等待真实总线变化。消费失败只在状态中记录异常类型，并等待事件或显式重启，不以日志事件触发自身循环。
- `close()` 取消并等待消费者，不删除已排队资料；服务恢复后继续处理。用户停止主会话会取消已接受但未消费的注意事项，去重凭据保留，不自动重投；之后新出现的事件仍遵循策略。`enabled=false` 额外取消所有尚未消费的注意事项，阻塞尚未开始的独立外发；已经生成的模型回复和通知仍留 WebUI，已经开始的 HTTP 不保证撤回。
- 模型执行失败与其它主会话运行一样留下失败状态，不自动重跑；原始通知和管理记录仍可查看。

组合层接线：在 `Runtime` 创建后、提醒/版本检查等生产者启动前构造 `AttentionInbox(runtime)`，以固定首次启用的游标。`await inbox.start()` 放在 `runtime.startup()` 之后。热配置时在替换配置前 `await inbox.close()`，新配置或回滚重建完成后 `await inbox.reconfigure()`；这两个入口自身不会同步取得运行时配置锁，后台工作才取得锁，因此可在配置锁内调用。关闭应用时先 `await inbox.close()`，再关闭 Runtime/Store。`inbox.status()` 返回 enabled/events/running/cursor/pending_batches/waiting/last_error，可用于管理页；`waiting=main` 表示等待主任务，`waiting=work` 表示等待其它执行任务、主队列或团队报告交接。`attention.queued` 事件携带入站 receipt，后续使用既有 `message.completed`。

测试全部使用临时数据库、模拟模型和模拟版本 HTTP 响应。覆盖首次历史跳过、来源核验、逻辑去重、批次合并、原子回滚、只读权限、流式不被提醒中断、owner 两次写操作完整执行、关闭消费者不取消 owner、配置锁竞争时的新 owner 优先、主助手先回复后的队友续办、团队终态到报告投递的间隙、无运行时任务的活动工作流、离线 owner 输入优先、路由隔离、队列背压，以及取消订阅后保留已接受批次；没有连接真实模型、渠道账号或操作桌面。
