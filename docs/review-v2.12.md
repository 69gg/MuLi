# 2.12 事件订阅与连接归属审查

状态：前后端并行实现，尚未整合、完整验证或发行。2.11 完整标题目录另行发布；本片不重写主聊天 hydrate，也不宣称完整首屏、单条 SSE、活动正文或浏览器内存已受总预算约束。

只读调研复现全局首连从 0 跨批回放旧事件，同一批完成事件触发大量重复会话和通知读取。方案先取得精确全局位置，再读取当前事实，从该位置接续失效通知；两类摘要分别合并在途请求，显式操作等待其调用后开始的读取轮次，不等待持续事件安静下来。旧连接的成功、错误及 401 均需验证所属连接，包含全局事件派生的读取。

独立设计评审阻止了三种不完整方案：共享直到 dirty 耗尽的 promise 会拖住工作流操作；通知页面的直接读取及已读操作会绕过摘要槽；仅在全局事件回调入口检查归属，不能阻止它已经启动的子请求迟到退出新登录。另确认重连若跳过旧事件，必须重验证当前可见管理页与已打开的只读详情，编辑草稿保持；不能把隐藏的旧缓存标为最新。

真实 Runtime 反证发现终态事件早于电脑引用清理，session 的 idle/paused 在清理后才保存，后面却没有失效通知。根修复复用 Store.event(objects=...)，仅当前 run 仍拥有 session 时，把最终 session 事实和窄 session.updated 事件同一事务保存；句柄移除、压缩采纳和主会话唤醒前不增加挂起点。之后复用既有取消隔离收尾唤醒订阅者，普通通知异常不覆盖已知执行结果，取消仍在完成收尾后传播。

四项成功、失败、暂停与取消的 cleanup 门控在修复前失败、修复后通过；另验证旧 run 不发布或改写新代，以及通知等待期间重复取消、普通异常仍保留持久终态和已移除句柄。新增七项加现运行、团队收尾与电脑接线共 48 项通过（0.55 秒），Ruff 和严格类型检查通过。仅临时 SQLite、假执行器和门控清理，无真实模型或设备操作。此结果不是整版验收；后续整合与远端证据继续补记。

后审查发现，driver 移除 session 槽后仍可能等待通知，原 close 无法再发现它。新增独立 finalizer 集合，关闭 Store 前等待该通知及诊断落盘。再审查发现取消 close 等待者仍可能跳过后续收尾，改为共享一次内部关闭任务，所有观察者等待同一收尾，取消在资源关闭后传播。真实同 sid 新旧 run 交接、旧通知成功/失败、关闭期间新 driver 清理与旧 finalizer 并存、两次取消及并发第二次 close 均有门控回归；相关 54 项通过，受限 service 峰值 83.3 MiB、swap 0，72 个源码文件严格类型检查通过。
