# 暂停会话释放后台压缩额度

## 问题与修复

压缩额度同时统计执行中的任务和已完成、等待收养的候选。前台 run 暂停时，Runtime 会将 session 写为 `paused`，并在收尾时尝试收养摘要；如果摘要在收尾之后才完成，原先的完成回调只识别 `idle`，候选会一直保留。在额度为 1 时，其他会话因此无法开始后台压缩。

完成回调现在同时识别 `idle` 和 `paused`。这两个值来自现有会话生命周期；run 的 `completed`、`failed`、`cancelled` 都最终对应 session 的 `idle`，没有新增或猜测其他会话终态。仍处于 `running` 的会话继续等待现有的回放或收尾边界，不提前安装摘要。

收养仍复用现有配置指纹、前层 generation、原始前缀条数和摘要校验；不修改原始消息、不恢复暂停任务、不重试工具、不改变 Runtime 生命周期或压缩额度。该修复适用于共享 Compactor 的主会话、队友及工作流会话；本次新增回归直接验证真实主会话的收尾路径。

## 有界回归

新增回归使用临时数据库、真实 Runtime 驱动及进程内假摘要/假模型客户端，覆盖四种 run 结局（完成、失败、取消、暂停）与摘要先完成/后完成两种顺序。摘要先完成时，检查 run 仍运行、候选仍等待收养；终态之后，另一会话的摘要回调必须实际进入，而不只是检查计数或复制产品条件。原始历史消息须保持不变。

摘要任务的观察回调注册在 Compactor 自身回调之后，以事件门控确认实际清理已经结束，不手动调用产品完成回调，不依赖固定等待。测试结束统一释放门控并关闭 Runtime。

旧实现的 `late-paused` 单例已在统一 guard 下复现：另一会话摘要回调等待超时，1 failed / 2.20 秒，service 2.766 秒，内存峰值 63 MiB、swap 0。
