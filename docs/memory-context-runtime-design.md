# 最终提示中的记忆质量（2.40 方案）

2026-10-24。现有 SQLite 分层记忆、提炼、图查询、更正、冲突和遗忘继续复用。本片修复模型实际得到的记忆选材，不创建另一套记忆，不增加依赖、默认网络、后台轮询或持久格式。用户既有持续 YOLO 授权适用；下列实现选择由本项目作出，不视为用户另行指定。

## 已确认的问题

1. `MemoryPipeline.cached_context` 已按预算生成完整条目及显式正文节选，但 Runtime 未传本轮预算，随后直接切片整个字符串。`max_context_chars=16000`、记忆预算6000时，最终4000字符可截在 JSON 或来源元数据中，单元测试的完整输出不代表模型实际收到完整资料。
2. `submit` 的同步 hook 先保存当前输入的自动 episodic，然后 `_history` 用同一原文召回。合法 `context_limit=2` 时，同原文副本占据相关名额、主人侧写占另一名额，旧 NAS 备份流程可能落选，当前输入却重复进入 system 与 user。

## 实现合同

Runtime 在召回前分配本轮记忆块预算，保留现有整体上限、四分之一比例和外层提示开销；将剩余预算交给已有完整条目渲染逻辑。渲染器先保留完整身份、来源、冲突与分隔符，再分配正文，元数据放不下就整条省略。自动记忆不再用字符串切片满足预算；最终 `pack_context` 仍负责完整模型请求的总预算，不能以本片保证任意系统提示都能放下。

将现有 `_ContextPage` 与两流分配抽成共用的小模块，供流水线及没有 MemoryApplication 的 Runtime fallback 使用。保持现有公平规则、信任筛选和 JSON 计数；记忆关闭时不注入。显式注册一个可调用的预算适配器，仍能接受旧的一参数调用；Runtime 用明确类型调用其预算方法，不捕获 `TypeError` 猜签名。普通旧 `Callable[[str],str]` 仍只调用一次，结果超出预算时整体省略，不截断任意提供器字符串、不自动重试或改变回调。

宿主把本次提示完整保留的最新 user 消息真实 ID 传入选材；没有真实 ID 不猜来源。只排除仍可证明是该来源自动归档原文副本的 episodic：匹配确定性自动 dedup key、来源、kind/layer、初始 version，且 active、没有冲突。已更正条目、同源提炼事实、冲突资料及其他来源相同文本继续可用。用小主键投影识别该副本，不加载整篇来源或从正文推断身份。

在名额截断前排除，以现有有界本地候选补位；不扩大候选、图边或上下文限制。缓存已有重排顺序可保留，必要时仅作一次本地补位；不改变显式查询或缓存内容。沿用 revision、来源遗忘和更正的失效规则，不把本次排除写入数据库、全局缓存或后续不同输入。

## 验收

- 捕获真实 Runtime submit 后 FakeClient 实际收到的请求，长流程和主人偏好在可容纳时都进入，每条 JSON 可独立解析，来源/冲突 ID 完整，正文节选有标记；改变预算的下一次请求立即遵守，持久正文不变。
- `context_limit=2` 时原 user 全文仍在，system 不重复当前自动归档副本，旧流程和侧写均被选中；归档仍可显式查询。
- 同源提炼事实、已更正 episode、冲突条目、其他来源相同文本均不被误排；工具续轮、不同渠道主人输入、subagent 提示及重开存储按实际消息 ID 处理。
- 有预算适配器、旧一参数 hook、无 MemoryApplication fallback、记忆关闭、极小预算及超大 legacy 结果均有明确结果。旧 hook 抛出的 TypeError 原样传播，不调用第二次。
- 本地只用临时 SQLite、FakeClient 和门控，不连接真实模型或渠道；检查继续串行通过共享资源守卫，独立后审与相关回归后才发布。

## 实现落点

共用模块 `memory_context.py` 承担完整 JSON 两流渲染、按真实来源的当次过滤和 `MemoryContextProvider` 具名可调用适配器；`Memory.automatic_episode_id` 只查询主键及身份条件。Runtime 从当前配置计算预算并扣外层资料标题后召回；MemoryApplication 的适配器读取当前开关、字符上限和名额，通过 `context_for_prompt` 复用流水线，不重配置后台 worker，原 `cached_context` 仍保留默认配置上限合同。所有提供器输出均作整体超预算复核，未再切片自动记忆字符串；fallback 保持原最多五个名额并遵守更小的配置。缓存有效召回不足当前 `min(context_limit, max_candidates)` 时仅一次既有上限的本地补位，包含命中旧小名额缓存的情况；合并后的召回也受此上限约束，侧写保持独立双流规则，显式查询与缓存不变。

验收代码分别位于 `tests/test_memory_context_selection.py` 和独立 builder 的 `tests/test_memory_runtime_quality.py`；真实请求均由临时 SQLite 与 FakeClient 捕获。共享资源守卫下定向三个上下文文件 52 项、应用与流水线两个文件 25 项通过；7 文件 Ruff 和格式检查、5 生产文件严格类型检查通过。每条硬超时 30 秒，收到退出码 0 和守卫终态；峰值分别为 95.9 MiB、82.9 MiB 和类型检查 188.8 MiB，swap 0。独立后审及更广整合验收仍以最终记录为准。

## 保留边界

本片改进资料选材，不证明模型必然使用记忆或回答正确，不提供语义召回质量的全面评分。来源资料、旧偏好和旧任务说明均不是新授权。更正后的完整事实仍可能因既有候选或字符预算落选，不能将没有注入解释为没有保存。真实外部模型与个人渠道效果需另行验收。

## 独立 builder check

独立 6.1 sol 已只读核对设计、Runtime、压缩投影、归档与记忆实现：没有必须由用户补问的决定，合同可直接实施。最新 user 投影保留真实原 ID；自动副本 dedup、初始 version 和未解决冲突均可用小投影判别；现有 revision 机制可以复用。重点后审缓存过滤后的本地补位、名额截断顺序，以及配置缩小/关闭后的下一次请求。

实现前通过 Context7 核对 CPython v3.13.9 的[可调用实例](https://github.com/python/cpython/blob/v3.13.9/Doc/faq/programming.rst)及 [Callable 注释](https://github.com/python/cpython/blob/v3.13.9/Doc/library/typing.rst)。采用显式适配器，不使用异常重试或动态签名猜测。
