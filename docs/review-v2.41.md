# 2.41：Linux 资料收件目录

状态：实现、独立后审、受限完整回归及离线构件检查完成，远端候选与发行仍待核验。本文不以入口存在或定向测试通过代替正式发布。上一版交付见 [2.40 审查](review-v2.40.md)。

## 用户场景与实现

主人明确选择现存资料目录，之后新候选文件沿已有 Attention 进入同一主会话或冻结的默认通知渠道，主人可继续要求阅读和整理。宿主只提交元数据，不自动解析、入库或注入正文，不扫描历史，不让模型轮询目录。正文仍可由 MuLi 按既有文件权限按需读取；文件名和内容不变成主人指令或写入、派遣、配置、外发授权。

原生适配复用已有逐段 NOFOLLOW 目录原语与 asyncio FD 回调，用 stdlib ctypes 调用 inotify，不增加依赖。一个实例持有目录链 FD，祖先自身与精确下一段 entry 变化使本代失效。同步复核先处理排队失效，目录移走再移回不能只凭最终 inode 相同继续观察。普通文件 metadata、候选集合、未交付原生批次、持久记录与单位时间事实分别有界；无候选时没有合并/到期计时器。

独立有版本策略存于现有 Store，主配置与配置快照不增加字段；提供主会话专属 write 工具 `file_inbox_configure` 和同一认证的策略 API。保存只重配本来源，调用者取消时仍持配置锁等待所拥有的重配结算。候选、canonical 事件、冻结路由和额度同一事务提交，最终 Attention admission 在锁内重新核对当前期望策略、访问根、保留记录与精确 event ID。明确停用会撤销本来源尚未 claimed 的输入，不误取消主人或其它来源批次。

默认每小时最多八条候选事实，同一授权额外至多一条缺口事实；缺口也可能触发模型，不能只按 Attention 批大小估算费用。达到限额或覆盖不完整后持久暂停，不因重启或窗口过期自动恢复。`file_inbox_get` 的路径是观察时定位，`current_file_verified:false` 明示未核验当前版本。具体合同见[使用文档](file-inbox.md)与[方案](file-inbox-design.md)。

## 独立后审与修复

初稿经 builder check 收敛目录身份、候选状态、最终接纳和总量额度；将“不默认注入正文”误解为“禁止 MuLi 按需读取”的建议，经原始要求及既有权限复核后撤回。

实现后发现并修复以下问题，未通过放宽资源、期限、权限或格式合同处理：

- 撤销若加载全部历史提醒或由 ingress 历史外层扫描，会随运行时间增长；改由独立小型接纳标记驱动 ingress 唯一 ID。元数据被淘汰后仍保留 pending 标记，防止撤销漏掉旧提醒。
- 记录剪裁若按 JSON 来源 ID 扫事件历史，会在配置锁内重复全表工作；改为从有限记录取得已保存 event ID，按主键并核类型/记录 ID 删除，损坏记录不猜删事件。补 SQL 计划与实际 trace 验证。
- 原生适配失败先关 FD 再回调，随后检查已关闭 watcher 会把首因覆盖为 watch_closed，并可能错误撤销仍有效的覆盖缺口前资料；改为保留首次原因、不再检查已有 pending failure、拒绝暂停后的迟到信号。
- 初稿将 file_inbox 加进主 Settings，任意全量保存都会使旧版严格读取器拒绝未知字段，而格式声明仍为 1。发布前移除该字段，采用已有独立策略范式；不以忽略未知字段或虚报格式兼容掩盖问题。
- 独立策略已保存、来源正在关闭时若调用者取消，可能未重新启动监听；复用既有 owned cleanup 结算机制，锁保持到来源重建或失败结算后才传播取消。

独立复审未发现剩余必须修复的 P1/P2；跨版本读取、API 和完整回归分别完成下述实际检查，不只依赖静态结论。

## 未验收边界

macOS、Windows 无文件事件后端，明确报告不可用；这不阻止其它核心功能运行。Linux 需要 `/proc/self/fd`、目录链权限及 inotify 系统资源。高度活跃的祖先兄弟 entry 也计入原生批次预算，可能保守暂停。

inotify 不保证远端网络文件系统、挂载覆盖或停机事件完整性；路径复核不是并发 namespace 的原子锁，device/inode 不是跨机器永久身份。本片不自动补扫、重绑定、恢复缺失资料或判断下载完成，真实桌面通知和外部渠道投递仍须分别联调。

Linux 常驻服务重启/切换/回退三事务及此前间歇期限问题仍是独立工作，不能由本轮收件测试通过代替。后续持续任务见[迭代计划](continuity-extensions-plan.md)。
