# 停机升级已有数据格式

新版的长期问题关注需要新的配置和输入证明合同：`database=1`、`objects=3`、`configuration=2`、`ingress=4`、`outbox=3`、`memory=1`、`install_profile=1`。各平台新装直接使用此完整格式，无需操作。已有数据即使此前支持四渠道私聊接管，也需显式升级；启动时若提示 `store_format_upgrade_required`，先完成下述步骤。

## Linux 独立安装

先用原版本停止后台服务，并结束所有使用这份数据的前台实例，再用新版执行：

```sh
muli --data-dir "/path/to/your-data" upgrade-channel-ownership
```

将路径换成实际数据目录。命令只升级数据，不启动或停止服务，也不安装依赖。成功输出 `{"upgraded": true}`；已经升级时输出 `{"upgraded": false}`。之后使用原来的配置和数据目录启动新版，旧版本不能再打开升级后的数据。

命令沿用 `upgrade-channel-ownership` 名称，支持以下三种精确完整源合同：

| 旧合同 | `objects` / `ingress` / `outbox` | 其余四域 |
| --- | --- | --- |
| 完整初始格式 | `1` / `1` / `1` | 均为 `1` |
| 原 OneBot 接管格式 | `2` / `2` / `2` | 均为 `1` |
| 长期问题关注前的四渠道格式 | `3` / `3` / `3` | 均为 `1` |

每种源合同都直接升级到上述当前完整格式。升级在既有独占保护和原子提交中仅转换格式 marker，不改表结构或业务行；原身份、会话、历史、渠道归属与投递记录保留，不重发旧消息，`unknown` 投递仍需先核查。主配置文件不由此命令改写，缺少 `memory_watches` 时新版采用默认设置；已经整理完的旧资料不会为新关注补扫。

新主配置字段和可撤销输入证明不受旧 reader 支持，因此即使没有业务行迁移，也不能让旧库直接启动新版或让旧版打开升级后的库。`requires_migration=false` 只描述当前格式上的同格式更新判定，不能替代这次停机升级；托管跨格式切换仍不支持。

## 不支持或失败时

- macOS、Windows 的旧库及托管安装尚不支持此命令；继续使用原版本。新装不受此限制。
- 有运行实例占用时，先正常停止它再重试；命令不会等待、夺锁或结束进程。
- 缺少标记、未知或混合格式、残缺数据库、已有托管事务的库会被拒绝。不要删事务记录或手改格式标记。
- 失败不会报告成功。若提交结果不明，先查看错误；重试会按数据库中的实际格式判断，不自动重放业务操作。
