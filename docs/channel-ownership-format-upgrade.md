# 渠道归属的固定数据格式升级

新版正常启动只接受 `CURRENT_FORMAT_STATE`：`objects`、`ingress`、`outbox` 为 `2`，其余四域仍为 `1`。新装数据库在各平台直接发布该完整声明。已有完整全 `1` 库启动时返回 `store_format_upgrade_required`，不会先恢复输入或执行后台业务。

本片只提供 Linux 非托管库的停机升级。先用原发行版停止后台服务，并结束所有使用该数据库的前台实例，再使用新版执行：

```sh
muli --data-dir "/path/to/your-data" upgrade-channel-ownership
```

命令不启动或停止服务，不读取模型配置，也不安装任何包。成功输出 `{"upgraded": true}`；库已经处于目标格式时输出 `{"upgraded": false}`。随后可用原来的配置和数据目录启动新版。Windows、macOS 的已有旧库继续使用旧发行版；本片尚未提供这些平台的停机升级入口。

升级复用 journal 控制者锁、数据库 writer lease 和构造锁。writer lease 按数据库规范路径选择固定 inode，使用自定义 journal root 的运行实例也会持有同一个锁。存在活跃 writer 或构造器时立即拒绝，不等待、不夺锁。它约束遵守现有写入协议的 MuLi 进程，不是对任意同权限外部程序的恶意改库防护。

命令只识别完整全 `1` 源声明和完整目标声明，并核验现有 Store/main 身份、完整 schema 与数据库文件身份。无标记库、混合或未知合同都拒绝，不从表结构猜格式、不为旧库补新建认证。

显式 `--managed-root`、默认 journal 中的现有事务或 selector，以及数据库中已有的托管归属证据均不支持此入口。数据库证据包括管理投影、`adopt`/`switch` 计划和带事务的管理计划；尚未产生首个投影的待应用计划也会拒绝。不要移除这些证据或手改标记来绕过拒绝。现有托管同格式切换仍要求双方读写格式与观察值完全一致，不提供全 `1` 与目标格式之间的 A/B 切换或回退。

唯一持久变更是在 `synchronous=FULL` 的一个 SQLite 事务中，将完整源标记替换为完整目标标记。它不重写对象、历史消息、入站 ID、空旧收据或出站状态，不推断任何渠道归属。新版渠道实现负责保留这些旧事实的重投与历史语义，`unknown` 投递仍不自动重发。提交前失败回滚；提交或提交后核验失败时不返回成功，重试依据库中实际完整标记判断，不承诺撤销已经完成的提交。
