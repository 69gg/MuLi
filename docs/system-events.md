# 系统事件与故障提醒

沐璃可以在空闲时解释已记录的系统故障、新版本和管理结果。主任务、队友或工作流还在运行时，会等待它们结束，不打断当前回复。让 AI 解释需要配置主模型，可能产生模型调用费用。

## 默认会提示什么

默认开启系统日志采集和提醒，级别为 `error`：记录错误及更严重的问题，并交给沐璃处理。当前自动接入的故障包括：

- 主助手、队友和工作流的实际执行失败。有父会话报告路径的队友失败沿本次执行的原报告交接，同一条故障日志保留供查证，不再额外唤醒主助手；工作流仍沿原终态报告处理，不因此追加外发。
- 扩展目录自动监视出现的新失败。
- 已投入使用的 MCP HTTP/SSE 连接首次发生接收故障。
- 已启用的后台语音不可用或监听失败；同一故障期只提醒一次，真实监听恢复后再次失败才新报。
- Telegram、微信后台接收不可用或失败；同一故障期只提醒一次，完整接收和本地保存进度成功后才恢复。

新版本发现和配置、更新等管理结果也可作为主动事项处理；它们由各自的设置控制，不受日志级别筛选。提醒与更新的用法见[提醒与主动事项](attention.md)。

上述合并只针对可核实父会话报告路径的本次队友执行失败；渠道代管仅留本地报告的失败、其它没有父报告路径的会话失败、队友运行期间其它组件的错误和主会话故障，仍按原设置提醒。

已查到新版本、沐璃尚未处理提醒时，后续临时检查失败不会抹掉这次发现。设置页仍会如实显示最近检查失败；同一版本恢复后不会重复提醒。提醒本身不会安装更新，更新前仍需重新核验并取得你的同意。

这里**不会自动收集所有第三方日志或每个组件捕获的异常**，也不会扫描系统日志来猜测发生了什么。没有提醒，不代表没有故障。日志只提供诊断资料，不是新的主人指令；沐璃不会借此自动更新、修改配置或派遣任务。

## 调整提醒级别和开关

可以直接说：“保持系统错误提醒开启，也把 warning 交给你解释。”沐璃通过现有配置流程提交变更；请以实际生效状态为准。

默认配置如下；需要手动编辑时，将片段合入已有配置：

```json
{
  "system_events": {
    "enabled": true,
    "notify_enabled": true,
    "capture_level": "error",
    "notify_level": "error"
  },
  "attention": {
    "enabled": true
  }
}
```

要包含警告，将 `capture_level` 和 `notify_level` **都改为 `warning`**。只降低通知级别，不会补出未采集的警告。也可设为 `critical`，只处理更严重的问题。

| 你想做什么 | 修改哪项 |
| --- | --- |
| 暂停日志引发的 AI 提醒，继续记录 | `system_events.notify_enabled=false` |
| 停止新的系统日志采集 | `system_events.enabled=false` |
| 暂停全部主动关注，包括故障、提醒和更新的 AI 处理 | `attention.enabled=false` |

关闭采集或提醒不会删除已有历史。`attention.events=[]` 关闭提醒、更新、管理和收藏资料整理失败这四类，不能代替总开关；收藏资料失败提醒直接使用主动关注，不受系统日志采集级别控制。总开关也不取消你已经登记的独立定时委托。重新开启主动关注不会补发关闭期间的全部历史。

## 提醒会出现在哪里

能够核实来源的主会话故障保留**原请求来源**，不会改投后来打开的会话或最近联系人。没有可靠来源的旧事件留在本地。

自主更新检查、扩展目录监视、MCP 连接故障和后台语音故障等独立事项默认留在 WebUI。需要向手机提醒时，在 **设置 → 消息渠道 → 主动通知** 中明确选择默认目的地，并开启主动外发；已有来源的事项不会因此改址。详见[默认通知设置](channels.md#无发令会话时的默认通知)。

普通说明仍保留在 WebUI；外发须显式使用发送工具，并受原事项保存的目的地和当前权限限制。排队、已接纳不等于平台送达；显示“结果未知”时不会自动重发，先核查发送记录，避免重复通知。

## 让沐璃读日志

可以直接说：

- “只读查看最近的系统错误，告诉我发生在哪次运行，不要修复。”
- “查一下这次失败的运行 ID，再读对应诊断，区分已确认的问题和推测。”
- “读取最近 30 行服务日志，先说明能查到什么，不要重启服务。”

沐璃可用 `self_events` 分页读取保留的错误记录，用 `self_failure` 按运行 ID 查有限故障位置，用 `self_logs` 按需读服务日志。事件摘要不包含异常正文或完整堆栈；日志可读范围取决于安装方式和服务日志是否可用，空结果不能证明从未出错。原始日志与事件记录的区别见[故障诊断](failure-diagnostics.md)。

## 没收到提醒时怎么查

先确认服务在运行、主模型已配置，且 `attention.enabled` 与日志提醒开关已开启。也可以让沐璃“通过 `self_status` 只读查看系统事件状态，并核对当前主动关注设置”：

- 主任务仍在运行：模型说明会延后，先看原任务状态或通知。
- `queued` 有待处理记录：尚未全部持久化，不等于已经提醒。
- `overflow` 或丢弃计数增加：部分事件未被保留，不能据此推断没有其它故障。
- `last_error` 非空：采集、保存或通知链有异常，先查已有记录，不自动重启或反复重发。

相同故障可能合并计数，旧记录也会按保留上限清理。需要继续排查时，提供准确运行 ID、时间和已看到的错误码，比只说“没有提醒”更有帮助。

开发者需要查接口、事务、去重、权限边界和历史验证时，见[系统事件实现说明](system-events-implementation.md)。
