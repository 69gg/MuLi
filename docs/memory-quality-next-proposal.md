# 下一片记忆质量候选：冲突证据共同呈现

2026-10-24。仅为基于当前源码的候选建议，尚未批准、实现或运行验证；不属于接办功能的交付范围，也不构成发行承诺。本轮只读研究现有记忆实现、相关测试及文档，没有调用模型、网络或检查命令。

## 为什么选这一项

私人助手积累的偏好和操作习惯会变化。假设主人曾说“备份直接覆盖”，后来又说“备份先离线校验”；尚未明确选择时，助手需要知道双方说法以及冲突仍未解决。只因本次查询命中新说法，或旧说法较新、置信度更高，就单独呈现其中一方，容易形成不完整的判断依据。

这不是当前权限漏洞或已证实的错误回答：现有提示已经保留 `status=conflict` 和对方 ID，模型也可主动核查。候选要改善的是**真实模型请求中可见证据的完整程度**，减少模型自行发现另一方、再调用工具的负担，而不是保证模型一定正确作答。

## 已有能力与确切缺口

| 已有能力 | 当前代码与回归证据 |
| --- | --- |
| 可信来源与逐字引文 | `memory.py` 的 `register_source` / `_validate` / `apply_extraction`；`test_memory.py::test_layers_sources_and_owner_trust_are_separate`。来源、信任和模型文本分离，不应重新建设。 |
| 互斥事实槽位、冲突与选择 | `memory.py::_save` 按同 `claim_key/layer/trusted_owner` 标记不同内容；`get` 返回冲突对方 ID；`conflicts` 可读双方；`resolve_conflict` 保存修订、将另一方设为 `superseded`。`test_conflicts_are_explicit_and_resolution_retains_provenance` 已覆盖选择与重新选择。 |
| 更正、遗忘和缓存失效 | `Memory.edit` 保留来源和旧快照；`forget_source` 来源级删除；revision 驱动查询缓存失效。`test_memory_context.py::test_conflict_resolution_refreshes_both_streams_and_keeps_status` 已验证解决后提示只保留生效方。 |
| 来源关系与检索 | 关系引文、别名贡献、多跳路径、关键词/向量融合及可选重排均已有，见 `docs/memory.md`。不能把本片说成首次增加关系出处或冲突检测。 |
| 完整预算与相关事实/主人侧写两流 | `memory_context.py::_ContextPage` 保留完整来源、状态和冲突 ID，`render_context` 先预留元数据再分配正文；Runtime 已传当轮预算。 |

缺口位于最后一行的选材单位：`recalled_for_prompt` 与 `render_context` 按独立记忆条目截断和分配名额，不把冲突双方作为共同证据选材。`Memory.owner_profile` 也允许尚未解决的冲突记录参与侧写；这是当前公开行为。

现成的真实请求回归 `tests/test_memory_runtime_quality.py::test_submit_keeps_complete_memory_pages_and_immediately_honors_smaller_budgets` 就构造了旧操作方案与新方案冲突，然后明确断言模型只得到新方案和另一条独立偏好；旧方案仅以 `conflicts` 中的 ID 出现。`test_memory_context.py::test_conflict_resolution_refreshes_both_streams_and_keeps_status` 在两方都命中且额度充足时验证双方状态，但没有要求单方命中或额度不足时共同呈现。

因此不是“遗漏了冲突标志”，而是“已知存在冲突，却没有保证相关双方正文一起可见”。目前没有运行新探针；上述判断来自现有代码和测试断言，不将其冒充新测得结果。

## 两种最小方案

| 方案 | 行为与代价 |
| --- | --- |
| A：冲突时只提供待核查提示 | 自动提示遇到未解决冲突，不交付这一方正文，改为含真实记忆 ID、来源 ID、当前 revision 的待核查资料。显式 `memory_query`、`memory_conflicts`、来源页和解决入口不变。最小、无需额外读取，但会抑制本可解释的证据，模型仍需主动核查。 |
| B：有限双方共同呈现，放不下则提示 | 对原本会被选中的冲突条目，额外读取至多一个实际登记的对方，作为同一未解决冲突的证据一起交付；无法完整表示双方身份元数据或条目额度不足时，整体降为待核查提示，不能只留下其中一方正文。无需新工具或持久字段，但需给选材和预算分配增加小型组合规则。 |

建议 B，并保留 A 作为预算不足时的行为。它给私人助手更多可解释的上下文，同时仍不选择哪方正确。此推荐是项目判断，不是用户已经确认的需求。

## 推荐方案的最小实现边界

- 只改变自动记忆提示选材与渲染；显式检索、管理详情、原文分页和 `memory_conflicts` / `memory_resolve` 的原合同保留。复用 `memory_context.py`，流水线与 Runtime fallback 共用规则，避免两套行为。
- 复用已经召回条目的真实 `conflicts` 关联，只尝试其第一项对方；不全文搜索、不按内容猜冲突、不递归追冲突链、不枚举全部冲突。一次原候选最多多一次对方点查，再对双方 ID 去重。多方冲突标明仅展示登记的一组证据，不宣称已经列全或解决。
- 对方增量点查必须在 SQL 中先限制元数据与正文片段字节，再进入 Python；不调用会展开其全部冲突/关系的 `Memory.get`，不调用会加载多组双方完整内容的 `Memory.conflicts()`，也不读取 source 全文。来源、信任、同槽位和当前未解决关系均须再次核对；关联失效或损坏只提供待核查提示，不另找无限替代项。
- 新增读取次数上限由现有 `context_limit` 和 `max_candidates` 推导，不增加隐藏倍增循环；选中双方各占一个原记忆名额，共享原字符预算。若已有双流公平规则还需为独立侧写留位，组合放不下就降为一条待核查提示，不破坏原保证。具体内部函数签名留给实施时的小范围设计，不新增配置字段或常量渠道。
- 双方完整 ID、来源、信任、状态先作为不可拆元数据预留，正文仍沿用显式节选。双方正文都应有可读片段；仅能放下空节选标记时降为提示。提示也需完整预算，连提示元数据都放不下则整体省略，不能裁剪 ID 或 JSON。
- 不根据 `updated_at`、检索得分或置信度选择赢家。未认证来源不能借组合成为主人偏好；维持现有信任分层，不把资料当命令，也不赋予任何工具权限。未解决冲突不会被后台自动 `memory_resolve`。
- 组合在构造请求的本地同步路径完成，不新增 await、网络、worker 或轮询；缓存中的候选只能作为候选，关联/状态按当前 revision 核对。编辑、解决、遗忘后的下一次请求必须生效，不承诺撤回已经发送的请求。
- 不新增 SQLite 表、主配置字段或 Store 格式，不改变旧记录可读性。不声称因此将旧 `Memory.get` 的全关系/全冲突列表读取、图查询或整条 Runtime 请求改成有界；本片只约束新增工作及最终提示预算。

## 可证伪的离线旅程

使用既有 `make_runtime`、真实 `MemoryApplication`、临时 Store 和 FakeClient。关闭自动提炼及媒体服务，以真实来源登记/确定性提炼夹具建事实；不替换 `Runtime.submit`、记忆 provider、查询或渲染函数。FakeClient 只检查实际模型请求，不能用它预设的回答证明自然模型质量。

1. **单方命中仍可核查双方。** 登记两个真实 owner 来源，事实同为 `nas.backup` 槽位；只有新方案含独特查询词，旧方案不含该词。额度可容纳双方及一条独立主人偏好时，通过真实输入触发请求。断言模型获得双方内容片段及各自来源、均明确未解决；不能仅留下新方案和另一个 ID。原始来源正文不应被整篇注入。
2. **名额与字符不足不单边失真。** 名额降为一、或让双方身份元数据超过本轮预算，下一次真实请求只能出现待核查提示或整体省略；不得出现任一方的事实正文冒充唯一候选。较小预算不造成越界 JSON；独立无冲突偏好按既有规则参与，不能因一个大冲突组被全部饿死。
3. **主人明确选择后即时更新。** 沿现有入口选择旧方案或更正后选择新方案，不换查询、不重建应用；下一请求只呈现当前生效事实，旧缓存不能复活被取代方，不再出现未解决提示。修订和真实来源仍可核查。
4. **遗忘、异信任和多方压力反例。** 来源级遗忘一方后，下一请求不包含被忘内容或旧来源 ID；未认证来源不能制造主人偏好冲突。三方及更多冲突只增加一次对方点查，不递归、不暗示证据完整，预算不足则降级。坏关联不能触发补扫或读取其它来源全文。
5. **工具续轮与重开小例。** 第一请求后做一次真实无害工具续轮，确认组合不因后续消息压缩变成无标志的单方正文；随后正常关闭并重开同一临时数据库，沿相同输入核对当前选择/遗忘仍生效，不重新提炼或复活原文。

验收同时观察模型请求、Store 无新增写入、source 全文读取被禁止、增量点查数量和最终 JSON 总预算。至少让单方命中场景在旧实现上确定失败，再验证候选实现通过；不能只测 renderer 的理想输入，也不能只断言 FakeClient 输出“请确认”。所有实际验证须另行授权检查槽并走既有 `check_local.py`，本提案没有执行这些步骤。

## 取舍与下一步

主要风险是占用两条名额会减少其它相关事实，所以必须保留组合降级和双流公平，而不是无条件补齐全图。另一风险是把一组双方误称为全部矛盾；必须明确有限样本，只有既有显式解决入口能改变持久状态。

暂不推荐先做自动时间失效：当前只有来源/修改时间与检索新近性加分，没有显式适用区间；把“较旧”视为“失效”容易误伤长期身份和偏好，显式时间元数据还需额外确认授权及兼容设计。冲突共同呈现复用现有事实、关系与 revision，更适合下一片小范围质量改进。两种方案都仍是候选，本次文档不授权实施。
