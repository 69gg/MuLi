# 失败后改交草稿的接办旅程

`tests/test_task_handoff_runtime.py` 用真实 Runtime、任务控制、持久队友、工具处理器和报告入库跑通以下离线路径。模型响应由 FakeClient 决定，渠道 HTTP 使用显式替身；这不是自然模型自主接办或真实渠道送达验收。

1. 主人在 Web 上传文件并要求整理、发布。主助手保存完整任务说明，显式把附件 ID 和任务 ID 交给原队友；宿主没有把文件正文注入模型。
2. 原队友通过既有 `channel_send` 发起一次投递。HTTP 替身模拟读取超时，持久投递成为 `unknown`；原队友用 `channel_status` 核查后失败，真实队友报告保留失败状态。
3. 主人在 Web 更正旧记忆，通过既有 Web 控制接口暂停、追加“只交草稿，不得发布”并请求重规划。开发中的手机分支改走经签名与原始账户核验的 OneBot `/任务`、`/暂停` 和 `/调整`，并重投同一暂停事件证明只生效一次。主助手显式查询更正后的记忆、读取完整任务说明，在下一轮用既有 `task_approve_plan` 确认方案；空 targets 不重启原队友。
4. 确认方案使此前的 handoff revision 失效。主助手重取指定原队友的有限索引，核对当前 epoch、记忆版本、失败执行及 `unknown` 副作用状态。索引不包含文件正文，也不证明外发成功或失败。
5. 主人经新的 Web 消息明确派工。主助手重新读取 handoff，从原消息项取得 `read.session_id`、`seq`、`revision` 和附件引用，显式派新队友接办。新队友先用 `conversation_read` 读取该原始消息，再用 `attachment_read` 读取文件，最后仅交草稿。

草稿队友冻结这次明确 Web 派工的 ReplyOrigin，报告沿既有队友报告链回到主 Web 会话。任务控制通知本身仍是任务控制来源，不借 handoff 选择外发目的地。原队友代次保持不变，渠道投递全程只尝试一次，新队友不调用 `channel_send` 或重新转写资料。

此用例没有替换 Runtime.submit、Team.send、任务核查处理器或报告持久化。它覆盖实际宿主接纳与工具选择后的行为；外部平台是否收到超时前的请求仍未知，生产故障恢复和自然模型决策质量不在此离线结果中。

手机分支复用 create_app 创建的当前 Manager 和 adapter，只把平台 HTTP 换为 MockTransport，保留真实最终准入闭包。三条控制确认回手机，原未知外发仍只尝试一次；重规划主输入直接核对 route=null 与原任务控制引用，最后新 Web 明确派工及草稿报告仍回 Web。两条参数化旅程已通过受限检查；手机能力尚未发行，压缩和进程重开组合仍须另验，详见[手机候选记录](mobile-task-control-proposal.md#本地候选与独立后审2026-10-24)。
