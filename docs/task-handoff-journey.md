# 失败后改交草稿的接办旅程

当前发行：显式手机控制与压缩重开组合已随2.45发布，主运行的手机重规划回复已随[2.46发布闭合](review-v2.46.md#发版闭合)。下文逐轮候选验收经过保留为历史记录；独立完成回报的2.47候选已[本地闭合](review-v2.47.md#最终候选准备)，远端与发行待验。

`tests/test_task_handoff_runtime.py` 用真实 Runtime、任务控制、持久队友、工具处理器和报告入库跑通以下离线路径。模型响应由 FakeClient 决定，渠道 HTTP 使用显式替身；这不是自然模型自主接办或真实渠道送达验收。

1. 主人在 Web 上传文件并要求整理、发布。主助手保存完整任务说明，显式把附件 ID 和任务 ID 交给原队友；宿主没有把文件正文注入模型。
2. 原队友通过既有 `channel_send` 发起一次投递。HTTP 替身模拟读取超时，持久投递成为 `unknown`；原队友用 `channel_status` 核查后失败，真实队友报告保留失败状态。
3. 主人在 Web 更正旧记忆，通过既有 Web 控制接口暂停、追加“只交草稿，不得发布”并请求重规划。开发中的手机分支改走经签名与原始账户核验的 OneBot `/任务`、`/暂停` 和 `/调整`，并重投同一暂停事件证明只生效一次。主助手显式查询更正后的记忆、读取完整任务说明，在下一轮用既有 `task_approve_plan` 确认方案；空 targets 不重启原队友。
4. 确认方案使此前的 handoff revision 失效。主助手重取指定原队友的有限索引，核对当前 epoch、记忆版本、失败执行及 `unknown` 副作用状态。索引不包含文件正文，也不证明外发成功或失败。
5. 主人经新的 Web 消息明确派工。主助手重新读取 handoff，从原消息项取得 `read.session_id`、`seq`、`revision` 和附件引用，显式派新队友接办。新队友先用 `conversation_read` 读取该原始消息，再用 `attachment_read` 读取文件，最后仅交草稿。

草稿队友冻结这次明确 Web 派工的 ReplyOrigin，报告沿既有队友报告链回到主 Web 会话。任务控制通知本身仍是任务控制来源，不借 handoff 选择外发目的地。原队友代次保持不变，渠道投递全程只尝试一次，新队友不调用 `channel_send` 或重新转写资料。

此用例没有替换 Runtime.submit、Team.send、任务核查处理器或报告持久化。它覆盖实际宿主接纳与工具选择后的行为；外部平台是否收到超时前的请求仍未知，生产故障恢复和自然模型决策质量不在此离线结果中。

手机分支复用 create_app 创建的当前 Manager 和 adapter，只把平台 HTTP 换为 MockTransport，保留真实最终准入闭包。三条控制确认回手机，原未知外发仍只尝试一次；重规划主输入直接核对 route=null 与原任务控制引用，最后新 Web 明确派工及草稿报告仍回 Web。现三个参数均通过受限检查，新增参数覆盖真实压缩、完整lifespan/SQLite正常关闭、新Runtime重组和手机重投，再由新队友沿实际收到的fresh定位读取原证据。仅删除定位行的负控制必须被拒绝。该重开在同一pytest进程，不等于OS新进程或真实系统服务恢复；显式手机控制已随[2.45发布](review-v2.45.md#发版闭合)，真实模型和平台送达未验，详见[原候选记录](mobile-task-control-proposal.md#本地候选与独立后审2026-10-24)及[新组合证据](compaction-reopen-handoff-proposal.md)。

上述保留原接办切片的验收范围。新增 `tests/test_mobile_task_control_followup.py` 单独要求主助手对手机 `/调整` 的重规划说明回本次私聊：网页真实登记并派原队友，手机暂停使旧调用停靠，保留旧 Web 来源的真实暂停报告，提交调整后正常关闭并重开原 Store，再经真实 `commitment_read`、下一轮 `task_approve_plan` 和一次原队友计划交付生成说明。四个参数覆盖先前 Web/另一私聊、发送前撤销及一次 unknown 后重开不重发；Web 同时可见。原实现四项均已实际到达最终手机 outbox 缺失断言，修复后四项通过。此处显式回复来源不改变 route=null 的任务控制身份，也不改队友报告原来源；后续队友最终完成通知的持久订阅不属于本片。

历史2.46切片首轮四条新旅程及三项兼容/来源回归均已通过。十五文件首轮整合取得 429 passed、2 failed；两项是本页既有 OneBot 夹具把新增自动重规划说明计入控制确认，实际 outbox 已包含原 unknown、三条 sent 控制确认和一条 sent 自动说明。夹具现按真实 outbox 的 `automatic` 标记分类，精确核对三条控制回执及唯一自动说明的目的地、原始手机事件来源 ID、主消息对应的 outbox ID 和一次发送；普通阶段总数为 5，重开后额外旧码拒绝回执使总数为 6。成功后的 attempts 按 Manager 真实合同清零为0，一次发送由 HTTP recorder 证明；此前误预期1的两项夹具失败保留。原最终 Web 明确派工、Web 草稿报告与 unknown 一次且不重放的断言保持。此次只改夹具，三参数最终3 passed，十五文件最终431 passed，没有扩大超时或放宽计数。独立后审无剩余P1/P2，后续精确远端与正式发行已完成[2.46闭合](review-v2.46.md#发版闭合)。

新的[独立完成回报候选](mobile-task-completion-proposal.md)在 `tests/test_mobile_task_completion.py` 保留上述历史范围，另走原队友新代真正完成：重规划运行结束后，另一私聊8完成普通独立聊天，再释放队友真实写草稿；真实完成报告已提交且未发布时正常关闭重开，新的独立主运行须仍回原发令手机7。原三条 sent/blocked/unknown 旅程到达手机完成出站缺失的结果保留为历史目标红。十二参数覆盖准确 archive/受控有限 ingress 承接、逐字段损坏、原私聊8来源保留及同正文不同消息身份，已纳入21文件411项通过及独立后审，见[2.47本地闭合](review-v2.47.md#最终候选准备)；远端与发行待验。没有替换完成事务、flush 或默认工厂生命周期，不把正常重开扩大为执行中断自动恢复，也不宣称孙代结果自然回手机。
