# 手机渠道显式任务控制（2.45 候选）

本版让已绑定主人在 Telegram 或 OneBot 私聊中查询、暂停和调整具体任务，仍由同一个持续主助手规划，最终任务报告保留原来源。当前为本地候选，尚未远端 CI、合并、打发行标签或发布；真实账号未实测。

## 行为与边界

`/任务` 返回有限任务列表和可复制短指令；`/暂停 <短码>` 冻结该票据的任务控制双版本，回执给出 `/调整 <短码> 新的完整要求`。调整产生一个受保护的任务控制输入，`route=null`；主助手仍须读取完整说明、在下一轮确认方案并显式派工，不能凭确认自动恢复队友或工作流。已进入的操作可能仍在收尾，未知外发不自动重试。

首片只接受适配器核验的主人私聊原始纯文本。Telegram 要求可靠数字账户身份，OneBot 要求显式账户与原始数字 self_id 一致；群聊、引用、转发、媒体、ASR 和模型生成文本不能借用这条控制入口。短码是已有持久回执的定位，不是认证或授权。

复用既有 channel_inbound、TaskControl、配置锁、领域查重及版本门，没有新数据库或后台轮询。控制回执先保存，再执行原通知和本地确认队列修补；重复事件不重复控制或创建模型输入。确认结果 unknown 时不自动重发；本地队满不能回滚已经提交的任务控制。纯查询和暂停本身不新增模型输入，既有待投递报告仍可沿原路径唤醒主助手。

Runtime 在配置锁内核对当前 Manager、adapter、来源和主人身份，离开锁后执行通知，避免重入锁。手机扩展可选 expected_approved_epoch，Web 原 API 和既有请求指纹保持原形。短码索引至多读取两个候选；冲突、损坏、过期引用明确拒绝，不补扫更早记录。

## 独立后审与实际反例

## 正常压缩重开验收

[独立提案](compaction-reopen-handoff-proposal.md)新增节点已实际通过：真实Runtime自有压缩、完整lifespan/SQLite正常关闭、同一数据目录的新Runtime/create_app重组、手机旧事件幂等和旧票据/非主人拒绝，再由新Web显式派工读取原证据。根新节点1 passed（pytest0.73秒、guard1.414秒、95.9MiB/swap0）；整个旅程三参数3 passed（pytest0.99秒、guard1.705秒、105.5MiB/swap0），均实际exit0，不累加进全后端。

两次实际失败均保留：先误以为webhook会抛内部403，改为成功ack并完整断言无准入副作用；随后等新队友四秒超时，有限临时库显示主run先IndexError，原因是测试首次create_app后才安装场景工厂，PluginManager关闭时恢复了空基础FakeClient。现提前安装并核对正常关闭/新Runtime工厂身份，保留真实插件生命周期、四秒门与业务断言，没有生产修改。独立审查另补新队友从实际Team消息解析fresh定位并用于conversation_read实参，旧定位只作oracle；仅删实际定位行的负控制须失败。

交叉审查已先修两个验收缺口：长外发按渠道默认限额真实拆段，未知仅限已尝试首段，后续段不得尝试；最终“不外发”断言须等待持久事件游标越过对应 message.completed，不能早于异步消费者得到假绿。此方案不预判存在生产缺陷；正常同进程 Runtime 重开也不等同 OS 新进程、强杀、断电恢复或真实系统服务重启。

必要静态和构件检查、最终独立后审及精确远端矩阵仍须完成。自然模型能否主动选择正确工具、真实平台送达、未知副作用是否实际发生，以及真实系统服务整链，均不由 FakeClient/HTTP 替身旅程证明。
