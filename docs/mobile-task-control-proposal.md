# 手机上的显式任务控制（候选）

2026-10-24。已实现本地候选并完成定向回归、独立后审、基线整合、219文件完整后端及压缩正常重开组合；最终静态、构件、远端CI与发行仍待收尾，不是已发布能力或真实渠道验收。本文保留设计时缺口和验收清单，当前证据见末节。本片复用既有任务控制；普通消息仍进入同一持续主 MuLi。

## 用户得到什么

1. 在手机查看明确任务标题并复制短指令，暂停指定任务，不手输 ID、epoch，也不猜“这个任务”。
2. 暂停后追加“只交草稿，不得发布”，明确交主助手重新规划；不把发出一条聊天消息误称为旧计划已停。
3. 正常重开、历史压缩后仍能核对原任务并继续协调；未知外发不自动重发，原 Web 任务的报告不因手机控制而改投手机。

## 推荐：既有状态回执里的短引用

主人发送精确的 `/任务`，宿主回复一小页任务标题、状态和可复制指令，例如 `/暂停 8ac31f90d2b4-1`。暂停成功的状态回执提供 `/调整 新短码 只交草稿，不得发布`。每个短码只指向回执中一个完整任务 ID 和当时控制快照；不按标题、最近聊天或当前列表行号重新选任务。

短码建议由**该状态入站记录 ID 的固定短前缀＋页内序号**组成；具体长度由实现者固定并写回归，不作为配置。它只是既有 `channel_inbound.receipt` 的定位符，不是 bearer 权限或签名协议。receipt 增加小型版本化宿主元数据，保存本页任务 ID、epoch/approved_epoch、允许操作及原渠道账户、主人、私聊目的地；不建票据表、密钥或定时过期服务。解析用现有入站主键前缀范围最多取两条，碰撞、缺失、坏版本、超预算即拒绝，请主人重新 `/任务`；不扫描全历史找相似码、不覆盖旧回执。

首片建议限支持适配器的**私聊纯文本**：Telegram、OneBot 可先分别补原始信封判定；没有可靠证明的渠道继续普通聊天，不宣称具有控制入口。账户也必须有可核验的稳定身份；现有逻辑`bot` fallback不是真实机器人账户证明。OneBot只有在显式稳定账户配置与经官方原始信封核验的机器人身份一致时才能接纳控制；无法证明时默认拒绝，不为凑渠道数量放宽。命令必须整条匹配，不从自然语言、Markdown 引用、转发、caption、附件、ASR 或模型输出提取。保留前缀但格式错误的控制请求返回明确错误，不降级交模型猜着执行。owner 手动复制一条完整指令属于新的显式文本，不能承诺识别其人脑来源。

## 生产合同与现有缺口

- `ChannelManager._receive` 已有账户化事件键、信封指纹和入站回执去重；目前可信文本全部调用 `submit`。新增分支只接宿主判定合格的原始文本。`IncomingMessage.text` 现合并正文/caption 等，`reply_to` 现用于回复路由，**不能当作用户引用了某任务卡的证明**；需增加默认不合格的适配器来源标记，并补各平台原始载荷反例。平台细节实施时核官方资料，不凭当前归一化 text 推断。
- 由Runtime内部取得 `configuration_lock` 后，同步复核当前适配器实例、可靠账户身份、私聊路由和owner绑定，关闭、换账户或撤销绑定期间不得提交。复用`ChannelApplication`普通提交已有的同步admission guard模式；不在渠道外层持该锁再调用Runtime，不在guard中await，也不在该锁内等待close或`_inbound_lock`。当前close会取消并收拢入站，未发现既有必然锁反转；上述是新接线必须保留的顺序。旧短码本身不授予权限，账户缺少真实身份证据就拒绝。票据绑定原接收人，不能跨渠道、跨主人或跨目的地使用；不用群聊转发的任务卡控制私聊任务。相同身份恢复绑定后仍按当前授权与控制版本判断，不承诺永久吊销名单。
- 复用 `OwnerControlRequest`、`Runtime.submit_task_control` 和 `TaskControl.owner_control`。暂停分支不新增模型输入、不因命令本身启动重规划；已有待处理输入或报告仍遵循既有唤醒，不能承诺完全没有模型运行。调整必须针对已暂停任务，完整追加要求并request_replan。之后仍须主助手 `commitment_read`、下一轮 `task_approve_plan`，不自动批准、派工或恢复。活动工作流仍按现有 `workflow_active` 拒绝。
- 当前 `submit_task_control` 缺少渠道最终准入钩子，需按上述已有同步guard最小接线，不能在锁外检查后冒称原子接纳。顺序固定为：当前来源授权→解析不可变回执→既有控制回执查重→当前任务/控制快照CAS→提交。控制快照变化使旧码失效；不替用户换新epoch重试。额外快照校验必须位于领域层查重之后，避免成功后丢回包的重投被误报为旧码失败；保持原Web调用合同。
- 控制 request_id 从当前完整渠道事件键确定派生，不从短码派生：同事件同内容只提交一次，同事件改内容拒绝；另一个新事件复用已使用短码，按过期控制快照拒绝。短码无独立墙钟期限；依赖状态回执仍在、控制版本仍适用及当前授权，缺资料就重取。短码跨压缩/正常重开有效，不从摘要恢复缺失回执。
- 状态页、控制结果用既有 `channel_outbox` 发固定回执，确定投递 ID 去重，发送 unknown 不自动重发。状态回执先持久保存再排发送；重复入站须能补做**本地幂等入队**，控制已提交但确认未发不回滚任务、不重做控制。回执说清“暂停已登记，已进入的操作可能仍在收尾”；不能把入站成功说成全部工具已停止。
- 调整产生的主输入继续沿现有受保护 `task_control` 引用、route=null；控制确认仅回手机，任务/队友的 ReplyOrigin 不变。既有 `_repair_tail`、handoff、seq/revision 与附件工具负责核查续办；已经进入的副作用不承诺撤销，unknown 不重放。

## 备选、成本与首片验收

备选是“回复某条任务卡后发暂停/调整”，交互更短；但当前跨渠道没有统一、可信的被引用消息 ID，不能复用现有 `reply_to` 冒充。首片不引入各平台按钮、回调协议或模糊自然语言控制；普通“帮我改一下”仍按现有聊天行为处理。

状态页复用 `Commitments.list` 的既有限额和完整输出预算，只展示有完整 brief 的未完成任务；不查队友全正文，不调用模型。回执元数据随页预算限制；新短码解析最多两条索引候选，SQL 字节门后解码、再点查指定任务，坏项不补扫。列表和原 `TaskControl.scope/current` 的旧内部扫描成本尚无全面有界证明，本片不能用有限返回数冒称整链恒定 I/O；不新增后台轮询、下载或资源上限。

首片用临时 Store、真实 Runtime/渠道接纳/工具门禁、FakeClient 与 HTTP 替身证明：

1. **手机能可靠改任务。** Web 两个同名任务，手机状态短码只停指定一个；旧队友尚未派发的工具记 not_executed，其他任务继续。已进入的外发超时记 unknown、全程一次尝试；主人无需提供 epoch。暂停后取新回执调整，主助手按既有下一轮批准后仅交草稿，仍回原 Web。
2. **回执与权限不会漂移。** 当前绑定撤销/替换、跨账户/主人/目的地、缺少可靠机器人身份的fallback账户、配置与原始机器人身份不一致、引用/转发/caption/语音中的伪指令、错码/碰撞/坏回执、旧控制版本及同事件改正文均拒绝。模拟控制提交后丢返回、发送队列满及确认unknown，重复事件不重复epoch/要求/模型输入，不把未知确认自动重发。
3. **重开后续同一任务。** 压缩原聊天并正常重开，同主身份、控制状态和原报告来源保留；旧版码失效，当前有效码仍可定位。明确调整后沿 handoff 的原 seq/revision 读取资料，不复活忘记/丢失证据、不重放 unknown。旧客户端/旧版本不支持此入口不能称已有同等语义。

涉及生产位置预计为 `channels/types.py`、支持的 adapters、`channels/manager.py`、`runtime.py`、`task_control.py` 及 server 组合接线；沿用已有 channel/control/runtime 测试再加独立手机旅程。实施后同步 `channels.md`、任务控制使用合同、handoff 旅程及持续扩展计划。首片不做任意 DAG 暂停、自动接班、未知副作用重试、真实账号/语音/模型效果验收或服务故障恢复；这些不能由离线绿色代替。

独立只读方案后审已收口两项P2：暂停的绝对不唤醒表述、逻辑fallback账户冒充真实身份。本文已按现有代码收紧，并补同步准入与锁顺序；这属于方案修订，不是产品实现或回归通过。

## 本地候选与独立后审（2026-10-24）

核心与渠道分片均已冻结。新增 `mobile_task_control.py` 复用 `channel_inbound.receipt`，Runtime 持配置锁执行同步最终准入；领域层在查重之后核对 epoch 和 approved_epoch，原 Web 请求指纹保持。短前缀固定 12 位十六进制加页内序号，最多读取两个主键范围候选；状态页最多首批十项，不补扫。控制确认先持久化再排原手机出站，原任务报告来源保持。

根先实收领域双版本、领域查重顺序和 Runtime 锁内准入三项旧实现失败，再批准实现；首轮两份核心测试 36 项通过。独立后审另发现三项 P2，均先取得实际反例，再修复：

- Manager 预读损坏控制回执：坏 JSON、非对象、超额和坏 UTF-8 四项失败，改为只取四个整数标量；当前信封一律交核心读取唯一权威回执，旧回执只拒绝、不改写。
- 小身份字段被 SQLite 驱动提前解码：name、fingerprint、id 三项坏 UTF-8 失败，改为 SQL 字节门内 BLOB 投影后严格小字段解码；坏项仍占原 LIMIT，不过滤或补扫。
- 永久拒绝未转为渠道错误：真实 Application→Runtime 组合十项失败、六项基础设施保护通过。仅明确写入前拒绝使用 `MobileControlRejected`，应用转换固定 403；手机最终撤销同样 403。SQLite、保存、关闭与提交后通知的其它异常不被宽捕获，重投可恢复。
