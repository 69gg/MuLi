# MuLi 运行架构

MuLi 是服务于单个电脑用户的本地数字生命助手。界面保留十八岁少女的亲切气质，不模拟恋爱关系。所有执行能力通过同一个权限入口，模型只提出行动，运行时决定是否执行。

## 实现选择

- Python 3.12+、FastAPI、HTTPX、SQLite；不加载本地模型、向量数据库或 LangChain。
- 原生 HTML/CSS/JavaScript 工作台，无 Node 构建链。青瓷蓝、墨青文字、简洁会话布局；状态按需展开。
- `providers` 负责 Chat Completions / Responses / Anthropic 协议与原生工具回放。
- `runtime` 负责会话、流式输出、取消、预算、独立审查；`conversation` 维护持续主身份收件队列，`team` 管理持久队友与邮箱，`workflows` 执行显式 DAG。
- `task_control` 在已有工作账本上保存主人暂停、追加要求和主助手确认方案的事实；SQLite 短事务同时提交修订、回执与通知意图。模型请求携带完整说明的固定快照，运行器在进入工具处理函数前核对执行版本，团队生命周期负责暂停和有证据的续办。
- `compaction` 后台生成和验证分层摘要，`context` 以确定性节选和完整轮次淘汰整理最终请求；原生协议数据与持久历史不改写。后台摘要和记忆提炼不占前台模型执行额度，各自保持有界队列和单请求并发。
- 压缩的关闭与会话级清理各自持有可共同等待的收尾任务；清理期间停止产生和采用候选，模型 await 后复核任务所有权，外层取消不重复中断子清理。关闭先收取已有清理再释放引用，原文、长期记忆与正常关闭前的已采用摘要不因此删除。
- 工具后的实时补充不消耗待读回执。最终请求打包与后台摘要共同保护宿主标记的最新完整结果及其调用配对，直到实际助手回应或下一批调用；保护后的必要内容仍超限则明确拒绝请求，窗口外已经回应的旧结果可继续压缩。
- 历史选择达到摘要目标后，仍须包含已完成的助手回复才停止；较长首条输入因此不会阻塞整理。选择保持完整消息组、原有读取窗口和待读批次边界，不为触发压缩跨过未消费结果。
- `tools` 显式注册工具；文件系统、搜索、个人记忆、无障碍电脑操作共用权限门。
- `store` 使用 SQLite 保存消息、事件、审批、通知、运行和记忆；图关系与来源共同检索，不引入多用户隔离的复杂度。
- `memory_pipeline` 独立处理原文提炼、向量、社区与查询缓存；原文、别名贡献、实际遍历路径、冲突和来源级遗忘由 `memory` 管理。`memory_evidence` 以完整 JSON 投影模型查询及按需原文页，投影不修改缓存或改变身份。`attachments` 保存上传与生成文件，内容仅按需读取；`local_services` 提供统一文件引用和未完成工作账本。
- v2.64候选由 `memory_application` 将直接队友历史完成报告接入同一管线：Team完成事务之后的窄观察与正常启动补录共用准确事件/run/report证明和固定来源ID，不依赖当前agent最新代次。来源保持非主人信任，遗忘与作业去重复用现有机制，观察失败不阻断队友原收口。合同与未验范围见[队友报告记忆](team-report-memory-proposal.md)。
- `channels` 负责平台协议、身份绑定、附件和持久投递，`channel_application` 在配置锁内重新验证入站授权；普通回复在 WebUI 流式展示，外发由助手显式调用发送工具指定已核验目的地。
- `reply_origin` 在进入异步上下文钩子前冻结宿主回复目的地，与主人身份和任务授权快照分离。Team 的结果及来源沿既有事务进入报告/ingress；队列在回放安全边界按完整目的地分段，避免把多个渠道的新输入合成一段广播回复。旧无来源报告本地处理，不另建发送账本。
- `proactive` 区分原请求绑定、宿主证明的独立事项与旧本地来源，在事项持久产生时冻结选路；原记录与事件一起提交，Attention 核查原证据并按完整投递依据分批。`proactive_memory` 只读主键元数据，核验明确绑定的偏好版本和来源，不进行语义选路。会话回复只将完整终答交给既有 outbox，每段发送前重新检查授权与原依据。宿主审批提示复用同一 outbox，另有真实等待者末门。默认目的地不改变旧任务的去向。
- `personal_io` 组合可选截图、录屏、声学桥接及附件；`management` 在空闲边界应用校验过的自身配置或经批准的更新；`plugins` 从用户目录加载显式信任的扩展。
- Linux 同版本恢复由 `linux_bootstrap` 在业务库前取得 writer lease，`management_host` 持久准备计划，独立 `management_helper` 驱动已核验的 systemd 后端。新进程先被动验证再放行，`management_projection` 原子写回终态及原请求来源。业务库使用 WAL/FULL，关闭实际写入者后才释放 lease；跨版本安装不复用这套单安装身份协议。
- Linux 保留安装切换使用独立 protocol 2：`managed_preparation` 核验当前与候选安装，稳定 launcher 选择实际运行环境，固定 controller 复用同一 journal 和共享控制引擎。配置、选择记录、unit 与进程身份分别核验；失败回到旧安装时继续使用原数据库最新数据。管理入口接通 `self_adopt`、`self_switch` 和当前代恢复，监听变更也进入恢复事务；离线候选准备沿独立策略接通，另可批准精确版本的一枚 MuLi wheel 后有界在线获取，依赖仍仅使用明确本地材料。完整在线依赖求解与跨格式迁移尚未提供。合同和验收边界见[本地托管切换](managed-operations.md)和[有界在线材料](bounded-online-candidate-design.md)。
- `integrations.chiliarch` 使用真实 agent 配对、SSE、消息与 ACK 协议；收到事件先将 inbox、通知与事件事务持久化再 ACK。`integrations.attention` 使用默认关闭的独立对象策略，把当前配对身份的新普通消息作为外部资料交给 Attention，受锁复核 scope/revision；不自动回信，不改变主配置格式。空闲时不调用模型。
- `reminders` 等待最近到期时间或配置变更事件，通知和下一次触发在同一事务内保存；`tools.mcp` 仅在显式启用后连接扩展。
- `attention` 只消费有持久证据且策略允许的提醒、维护、新版、日志及可选 chiliarch 消息，等待活动工作结束后把游标、去重凭据和主会话入站原子提交。系统资料使用独立只读回合，不继承 owner 权限或历史渠道；外部消息正文另标为不可信资料。消费者等待事件变化，关闭不会取消正在观察的主任务，并先于 Runtime/Store 退出。
- 后台服务分别使用 systemd 用户服务、macOS LaunchAgent 或 Windows 无窗口计划任务。AT-SPI 通过 Linux 系统 Python 的 GI/Atspi 调用，避免在虚拟环境编译 GTK；实验性 macOS AX 使用系统原生框架与短期引用。Windows UIA MTA helper 已发布顶层窗口与选定树只读能力，以及实际对象的一次普通 Button Invoke；输入仍拒绝，Windows CI 自有按钮验收已通过，真实用户桌面未验，各平台分别报告能力。

无障碍读取分为有界应用/窗口发现与定向快照。宿主持有带有效期的原生定位信息，仅向模型返回当前临时标识；helper 在每次读取或动作前复核身份。工作量、省略原因与最终 JSON 大小分别核算，新快照失败也不会复活旧操作凭据。Linux 保持单次 helper；macOS AX 需要保留原生对象，因此使用仅归属于一个 session/run 的短期 helper。一次动作、到期或准确执行的终态回收全部引用，配置重载先完成旧对象关闭。协议只允许一个在途命令，发送动作帧前重验捕获的任务控制与新输入；不创建桌面轮询服务。见[电脑操作合同](computer.md)。

## 执行边界

`ask` 每个工具调用请求用户批准；`auto` 使用独立、无工具的模型上下文审查，风险操作和审查失败交给用户；`yolo` 自动执行已启用工具。三种模式都遵守输出和运行预算；访问根目录约束文件工具，shell 与桌面操作拥有当前用户权限，不是文件系统沙箱。子 agent 继承模式，不得自行提权。审批绑定工具参数及运行，不可重放到别的请求。

主对话、通知页与已绑定Telegram/OneBot原始私聊共用同一live审批。手机决定沿配置锁内
当前来源准入，将状态、事件及入站回执同事务提交后才唤原future；不提交新的模型输入，
不改变任务成果来源，也不从历史pending恢复许可。确认投递继续复用原持久outbox。
真实等待项还可沿本轮PreparedRequest冻结来源主动通知原Telegram/OneBot私聊：审批对象
与独立宿主来源证明同事务产生，原渠道消费者先持久入队再推进游标；不占主助手模型轮。
入队和平台发送前核原live future、准确run、停止、维护和当前渠道配置，失效blocked，
重开不补旧通知。详情见[手机主动审批通知](mobile-approval-notifications.md)。

可信主人新输入可撤销当前主运行尚未开始的旧审批。Runtime 在配置锁内以同一个 Store
事务提交输入与取消事件，提交后、首个 await 前用专用异常唤醒原 future。原工具结果以
`not_executed` 成组保存，再沿既有 claim / prepare 路径续办；不取消 driver 或队友。
重复、隔离资料、系统事项、已决定的票及已进入 handler 的操作保持原边界；模型流不
中断。故障与完整跨渠道旅程见[主人插话续办](owner-approval-steering.md)。

工作流是有限 DAG：节点依赖、并行上限、角色模型、每步工具预算和总时限。失败只影响依赖链，取消向下传播；重启后中断的运行标记中断，不自动重复有副作用的动作。模型可创建工作流；运行中不允许无界递归开队伍。

模型发起的子工作流绑定父运行。父 agent 释放共享执行名额后等待子结果，避免单并行名额下互相等待；父取消向下传播。主会话和工作流入口分别限制未完成任务数量，共享实际模型执行的并行上限。配置更新与新运行登记由同一把锁串行化，防止新配置与旧工具混用。

生命周期查询先筛未完成状态或精确父 run，再按稳定 ID 分页；最近历史页不参与恢复、子任务收尾或删除判定。恢复只校正状态，完成等待逐一检查同父运行的全部子结果，取消不会扩展到同会话的新一代。管理页另取全局活动运行的窄元数据，历史数量不会隐藏仍可取消的运行；分页和索引迁移边界见[工作流说明](workflows.md)。

主会话显示区分持久事实和进程活跃许可：`live` 快照以任务槽和未完成审批 future 核验当前状态，历史事件只恢复文本与过程；精确 `after` 连接后继会话 SSE。恢复状态与 `session.recovered` 原子提交，旧页面不因历史开始事件保持运行。工具 `unknown` 与失败、未执行分开显示，已知终态不被合成恢复消息覆盖；合同见[会话恢复技术归档](../devarchive/session-recovery-design.md)。

主人可从任务详情暂停一个账本所绑定的全部团队成员。已进入处理函数的操作允许收尾；尚未进入的旧副作用调用被拒绝，原生工具调用与结果仍完整配对。纯暂停不请求模型，也不能由模型自行解除。主人明确交主助手重新规划后，主助手须读取完整说明，在后续请求的固定快照上确认方案，再向指定未完成队友投递持久通知。通知记录证明送达，不等同于任务执行成功。活动 DAG 暂不支持中途暂停，相关请求原子拒绝，需先停止或等待结束；详见[任务控制合同](task-control.md)和[管理接口](task-control-api.md)。

运行记录目录使用独立的标题筛选和创建时间/完整 ID 续页，只读取摘要；具体正文沿消息序号和版本按需读取。目录分页不替代真实活动登记，不创建新聊天或主人请求，也不改变实时 hydrate/SSE 链路。预算、索引和数据变更边界见[记录目录](session-records.md)与[正文归档](history-archive.md)。

## 迭代与验证

1. 补记历史 v0.0.0；建立可运行的新核心、测试与文档。
2. 接通所有工具、主动事件、完整管理入口和用户服务。
3. 独立代码审查、故障/权限/恢复测试、真实浏览器验收。
4. 修复审查问题，更新版本与 changelog，签名提交并验证远端 CI。

自动化测试使用临时目录、模拟模型和本地协议服务，不访问个人文件、不操纵真实桌面、不调用付费模型。另在本机完成 AT-SPI 只读探测和 30 节点快照、真实浏览器界面验收，以及临时 MuLi 与 chiliarch 的配对/SSE/自我介绍联调；未连接真实模型、外部通讯账号，未实际录音、桌面点击或安装用户服务。完整结果见迭代与审查记录。
