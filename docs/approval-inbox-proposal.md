# 全局待批准收件箱

主人同时交给多个队友任务后，可以留在主对话，或从另一台设备打开同一工作台，看到所有仍真实等待本人的工具审批，核对对应会话、运行、工具、参数和原因，再逐项批准或拒绝。不需要逐个切换队友记录，也不依赖模型转述审批。

## 现状与最小改动

`Runtime.live_approvals()` 已要求当前进程存在未完成的 `Permissions.pending` 等待者，并核对持久审批仍为 `pending`。已有认证的 `GET /api/approvals` 返回该投影，`POST /api/approvals/{id}` 调用原 `Permissions.resolve()`。持久历史中的 `approval.requested` 或 `pending` 字样不等于当前可批准。

修改前，前端只展示当前会话的审批；全局事件虽观察到 `approval.requested`，但刷新通知不能补出全局审批入口。首片只修改 `web/app.mjs`，复用原审批卡片、`createSummaryLane`、`ownedRequest` 和每连接生命周期。没有新后端接口、数据库、工具、队列或轮询。

- 每个连接持有独立的 live 审批 lane。取得认证与全局事件位置后，原 bootstrap 一次读取 `/approvals`；全局 requested/resolved、执行终态和恢复事件触发合并刷新。
- 主对话原 `approval-region` 展示全局真实待批；通知页增加“待批准”标签，共用同一状态和原审批卡片，不增加侧栏。卡片保留会话/运行归属与实际工具参数，不能伪造当前主运行的审批。
- 按钮通过原认证 POST 精确处理一个审批 ID；每连接的处理中集合阻止同 ID 双击并发。只有原接口确认 `resolved` 后才更新成功状态，并重新核对 live 列表。失败保留可见错误，不假装批准。
- 另一设备处理后，resolved 事件刷新列表。关闭、超时、停止及重开后的历史审批均不能恢复按钮或重新授权。
- 登出和替换连接清空敏感审批状态、错误与处理中集合。旧 GET、旧 POST、旧 SSE 和旧 401 不能发布到新连接；迟到成功也不能删除新连接同 ID 的真实待批。

## 验收

正式后端旅程通过真实 Runtime/Team 工具执行创建两名 ask 队友。两个独立 ASGI 客户端分别认证，第二个客户端读取全局两个实际 `fs_write` 审批，准确批准一个、拒绝另一个。批准者只产生一次真实写入，拒绝者没有文件及 `tool.started`；重复批准原 ID 被原接口拒绝。后续真实停止一个待批队友，再在另一个队友实际等待审批时正常关闭应用，重开同一 Store 后历史仍可核查，但 live 列表为空、旧 ID 无法批准、没有自动重做。

前端使用既有 VM/最小 DOM 方法执行实际 bootstrap、SSE、渲染和按钮函数，控制的只有本地传输 Promise。首节点先证明认证连接及主会话正常，再准确要求一次全局 GET 和跨会话卡片；其余覆盖通知入口、另一设备处理、并发点击、失败、旧连接晚返回和登出清理。新增焦点回归先聚焦待批准页的实际按钮，再触发无关通知事件并完成其 GET，核对通知状态确实更新、当前焦点仍是文档内相同审批 ID/决定的按钮，且没有 POST。最小 DOM 沿既有工作流夹具模拟移除子树后失焦，不把脱离文档的旧 `activeElement` 引用算作保焦。循环 DOM 身份只比较布尔值，避免递归展开对象图。

这些夹具使用合成资料与固定模型策略，证明审批/界面合同，不代表自然模型质量、真实浏览器或真实渠道账号联调。

## 当前证据

- 首次前端执行因 VM 传入新对象后仍从旧对象读取 `ui` 而失败，属于夹具前置错误；根仅修正为同一上下文对象。
- 修正后真实认证 bootstrap 已结束、当前主会话正确，精准失败在全局 `/approvals` GET：预期 1 次，实际 0 次。测试 53.6 ms，守卫 135 ms、40 MiB、swap 0。此为产品目标红。
- 正式后端首跑在停止第三个队友时收到 415：夹具的 POST 未携 JSON，被原中间件拒绝；此前两名队友的实际聚合审批、批准/拒绝及重复处理拦截已经通过。这是夹具请求形状错误，不是新增审批授权问题。根仅补 `json={}` 后，完整正常关闭/同 Store 重开旅程 1 项通过，测试 0.68 秒，守卫 1.449 秒、109.5 MiB、swap 0。之后只将两处纯清理等待改用原 `test_attention.eventually` 的 3 秒有界让步：Team 的 `_done` 清理不保证再发事件，不能仅等总线；所有实际审批与效果 oracle 不变。改后同一正式旅程复验 1 项通过，测试 0.71 秒，守卫 1.445 秒、140.1 MiB、swap 0，不重复累计。
- 首批 7 项前端通过，测试 129 ms，守卫 206 ms、52.9 MiB、swap 0；加入同连接旧 GET 不复活审批、SSE 重连重取 live 后，9 个不同节点整组通过，测试 138.4 ms，守卫 221 ms、53.9 MiB、swap 0，不重复累计复跑。
- 后续源码审查发现，普通通知 summary 发布在“待批准”标签下也会重建整个通知视图，导致无关通知 GET 完成时丢失审批按钮焦点。根将该发布分支窄改为此标签只更新 chrome，由审批自身 lane 负责审批视图及保焦；其它通知标签仍按原路径刷新。加入第 10 个焦点回归后，10 项新增前端整组通过，测试 131.5 ms，守卫 238 ms、55.1 MiB、swap 0。
- 既有前端小组首轮有 23 项因清理访问夹具未创建的 DOM 节点失败；根改为可选 DOM 访问后，该组 55 项通过，测试 956 ms、82.9 MiB、swap 0。这不代表原后端权限门存在放宽。
- 全前端此前 296 项已通过，已包含前 9 个新增节点；第 10 项加入后，前端通过节点的去重并集为 297，不把新增整组复验重复计入。既有 API/发布兼容 5 文件共 233 项通过，测试 4.04 秒，守卫 5.399 秒、215.9 MiB、swap 0。加上正式后端旅程 1 项，本地共 531 个不同通过节点，详情见 [v2.58 候选审查](review-v2.58.md)。

## 不做

不增加聊天口令批准、批量批准、自动批准、权限模式升级、审批时限延长、重启恢复旧许可或自动重做工具。通知页只是同一认证主人的操作入口；队友、模型、系统事件或外部材料不能成为批准者。原执行末门、任务 epoch、维护门、拒绝语义和 unknown 合同不变。
