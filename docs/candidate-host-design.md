# 候选更新接入同一管理事务

这是 v2.23 的候选更新接入说明。候选核心和执行后端的定向验证分别记录在
[准备核心](candidate-preparation-core.md)与[进程后端](candidate-process.md)；
端到端安装、切换、回退尚须独立整合验收，不能由这些单元测试推断完成。

## 主人看到的操作

`self_config.candidate_update_policy` 或 `GET /api/management/update-policy`
读取完整候选策略。`self_update_configure` 与对应 PUT 完整替换策略；默认关闭，
不创建安装、不探测或运行 uv。策略存在原 Store 的独立对象中，主配置不加字段，
旧版固定恢复控制器仍能解析主配置。

`self_update_preview` 与 `GET /api/management/update-preview` 在配置锁下只读核验
真实当前安装、回执、本地 wheelhouse 和配置的 uv 文件，返回 `expected_policy`。
读取会探测实际 systemd 绑定、有限读取文件，但不启动候选进程、不生成计划。
预览中的 revision 是实际观察的匹配条件，不是可自行填写的资源授权。

主人批准 `self_update({version, expected_policy})` 后才排队。该工具沿现有真实用户
批准门，不因会话处于 yolo 自动放行；宿主从真实策略重新获取路径和预算，不采用
工具参数决定安装路径。原位旧资料库路径仍独立受原有安装/格式门约束。

## 一份计划和一份事务

候选更新计划第一次保存即为 `action=switch, operation=update`，携带目标版本、
批准时的策略、冻结的原会话路由。准备前再次核验这些观察；期间配置、策略、源安装
或材料变化使旧计划失败，需要重新预览。不会悄悄扩大预算或替换批准内容。

队列只在自然空闲边界领取计划。候选准备由同一管理 worker 强持有，状态为
`applying/candidate_preparing`；创建环境和等待子进程期间释放配置锁，因此普通
前台交互、设置读取和配置修改不被整个安装阻塞。修改使正在准备的旧候选观察失效。
四步依次验证 uv 版本、安装、依赖完整性、候选配置与新建 Runtime；所有步骤共享
一个总截止时间，每一步只发出一次。取消先由后端收尾它拥有的子树。

成功后重新取得配置锁，验证候选文件、证据和真实来源，向同一计划添加三个本地
路径和证据引用，再交给既有 `ManagedPreparation`。其 source guard 在 prepared
发布前每次重验候选与来源，包括等待 systemd 观察之后；发布后由既有账本、文件
身份检查和独立控制器接管，不再用旧 resolved 记录误拒绝本次合法新代次。

一旦 prepared 已持久化，即使 helper 返回丢失、取消或关闭，也保留同一 generation。
接续使用 `self_recover`，不重新安装、不延长事务截止时间。未发布 prepared 且已经
确认进程树退出的取消记录为 interrupted；无法确认收尾或宿主在准备期间硬退出时，
保留 applying / candidate_cleanup_required，阻止下一次准备叠加资源，普通对话仍可
继续。留下原路径以保留证据，不自动重跑安装。`self_recover` 与现有恢复 HTTP
入口会先核宿主绑定，再收尾同一计划内的候选；若已经发布管理事务则仍优先交给
原恢复控制器。未核空不能靠一次 not-found 或等到时间到来解除阻断。

计划中的 `candidate_protocol=1` 表示执行前必须同步保存 `candidate_process`。
四步均按 pending（启动前）、observed（发许可前）、settled（树空且客户端已收取）
写回原计划，仅上一步 settled 才能换下一步的进程身份。提交与事件是同一事务，
拒绝外层 SQLite 事务及不受支持的自动提交模式；整个计划继续受原预算约束。
提交已经成功但返回丢失时，宿主保留实际已写的附件，仍向后端传播错误，不能因此
发出许可；最终收尾也不能用旧内存副本抹掉更新的耐久附件。

重启时，只有协议 1 的 preparing 且尚未保存进程身份，或可信附件已经 settled，
才可记为 interrupted 并结束计划。旧协议、损坏附件及明确清理未知均保持阻断。
恢复只执行原身份的停止与核空，不执行候选命令、不增加期限、不自动重装。
恢复调用被取消或服务关闭时，仍强持同一次收尾，等待结果持久化后再关闭 Store。
普通配置锁只覆盖观察和最终写入，等待进程收尾时不占用它。

启用既有 `attention.events` 中的 `management` 后，精确匹配持久候选更新计划的
`management.progress` / `applying/candidate_cleanup_required` 会通知更新已阻断。
同一计划同一阶段只接受一次，重复进度事件不会反复唤醒。清理结束后的
`management.completed` / `interrupted/candidate_cleaned` 可报告“清理已结束，
更新中断”，不表示候选已安装或更新成功；其他进度与普通历史 interrupted 均忽略。
通知只带固定 action、operation、status、phase 元数据，不带任意错误正文或内部证据。
它保留计划的原回复来源，旧本地来源仍留在本地；管理事件不能借独立默认目的地
外发。注意事项继续使用原只读权限，不授予自动重装或重试未知效果的权限。

同一次内核启动中从未观察到的 pending 且单元缺席，仍不能解锁；真实内核重启后
才可在私有证据完整、同名无冲突的条件下确认旧启动已消失。证据损坏时继续保留
阻断，没有忽略证明的“强制成功”开关。恢复闭环已通过模拟宿主的整合回归，
尚未证明真实 systemd 崩溃与跨 boot 路径可用。

## 连续更新的依赖要求

`candidate_evidence` 与 `source_candidate_evidence` 只在计划中保存文件指纹。
证据正文位于最终保留目录的 `evidence.json`，包含完整原始安装要求和部署回执。
完整 requirements、约束和内部证据不复制到公开进度事件。

只读取当前账本 `request_id` 对应的一个有界计划：成功 switch 的 target 采用
candidate 引用；restart/configure、回退或中止采用 source 引用。引用的生产 ID
仍是原候选 ID，不要求等于后来重启计划的 ID。根据实际当前 prefix 限定唯一证据
路径，检查文件指纹、生产目录名、安装摘要和真实 receipt/intent，前后复核当前来源
及计划。没有祖先遍历、独立版本注册表或第二个活动选择器。

旧计划或外部 `self_switch` 可以没有引用，此时实际 receipt 必须独立证明可支持的
安装要求。已知 update 的目标证据缺失、已知引用损坏、回执变化或未知格式均拒绝，
不回退猜测原意图，也不把临时部署版本 pin 当作新的原始要求。运行旧二进制后产生的
不携带该证据的新计划可能使后续自动准备不可用；保留文件本身不等于重新取得证明。

整个计划按既有 journal 记录预算校验，并为固定控制器补充 transaction/终态结果
预留 4 KiB。准备中与加入引用后都复核；证据正文另有独立字节预算。旧投影通过
`{**plan, ...}` 保留附加字段，仍只认 canonical `action=switch`，无需修改旧控制器。

## 验证边界

临时 Runtime 使用全新默认配置与空数据库，只构造并关闭，不调用 startup、模型、
MCP 或用户插件；同时单独解析真实目标配置。它证明包导入、构造合同与新建格式可用，
不证明真实个人数据的迁移、外部集成或新服务已健康。实际切换仍须完整格式兼容声明、
被动启动及原有健康握手。

本地验证继续共用 `muli-checks.slice`，一次一个检查，不执行真实系统服务切换。
候选进程的 systemd 后端默认模拟测试；普通 stdlib worker 子进程只在检查守卫内运行。
没有把模拟观察描述为真实 systemd 全链路验收。

接入阶段的定向验证包括：配置/API 与既有管理 17 项、准备/投影/启动恢复
75 项、托管管理与宿主 19 项，以及新版提示 12 项。新增管理执行回归 14 项
覆盖审批快照、等待期间策略改变、取消与关闭、prepared 后返回丢失、未知收尾
不得放行；新增真实 Store/lease/投影的采集回归 16 项覆盖 receipt/证据漂移和
控制器、当前与候选三个不同目录的保护。后两组均硬拒真正的安装或服务启动。
这些数字只描述对应小范围检查，不代表完整测试集或跨平台发布验收。
