# 重建语义索引

更换 embedding 的地址、模型或维度后，原文、事实和关系仍在，但新模型不会使用旧模型的向量。可以明确说：“为这几份已收藏资料重建当前语义索引，不要重新提炼。”

只处理选中的完整来源，不会因为改配置、开机或查询就自动重建全库。长来源尚无原文块时，会在后台[补齐分块](memory-chunks.md)，保留原来的提炼记录和完成作业。

## 开始、查看与取消

主助手使用 `memory_reindex`：

- 开始：`action="start"`，提供准确的 `source_ids` 和稳定的请求 `key`。
- 查看：`action="status"`，提供原 `plan_id`。
- 取消：`action="cancel"`，提供原 `plan_id`。

开始前先确认来源。相同请求键和参数会返回原计划；不能借同一个键更换来源或模型。一次只保留一个活动计划，完成或取消后再开始下一份。

工具由主助手按当前主人的真实请求操作，遵守原来的权限、审批和维护限制。队友与系统提醒不能直接发起重建。

## 如何判断结果

`queued`、`processing` 和 `retry` 都不表示完成。查看真实状态中的来源完成数、已写入数、已存在数、遗漏数和错误；即使状态为 `done`，仍应核对 `omitted` 并实际查询。

后台复用现有 worker，不阻塞聊天，也不重新用模型提炼事实。每批后保存进度，正常关闭后可以接续；已成功写入且仍有效的向量会复用。更正、遗忘或来源版本变化会使旧的在途结果失效。

取消后不再提交尚未完成的结果；已经发出的请求仍可能收费。更换模型会阻断旧模型的活动计划，即使之后换回也不会自动复活，应明确创建新计划。

## 额度与设置

来源必须完整、未遗忘，且原后台整理作业已经完成。来源数量使用 `memory.max_pending_jobs`，完整计划受现有工具输出元数据预算限制。计划放不下时会明确拒绝，可以分次选择更少的来源。

普通后台作业与重建都有可运行任务时，按一项普通作业、一批重建轮流推进；只有一类可运行时，继续处理该类。等待重试时，会继续处理另一类已经就绪的工作。模型响应、维护暂停和重试仍会影响进度，不承诺固定完成时限。

当前计划及普通作业保存的分块沿用冻结参数。旧版已完成的来源按新计划开始时的策略规划；即使以前补过块，换用新请求键也会重新规划，策略不同可能增加条目和请求量。限额或设置变化导致计划无法继续时，应查看失败或阻断原因，不通过放大上限掩盖问题。

embedding 会向已配置服务发送原有记忆及原文块，可能产生费用。原文件保存在本地不代表向量计算也在本地完成。

## 管理 API

已认证管理入口为 `POST /api/memory/reindex`，参数与工具相同；`GET /api/memory/status` 的 `index_plan` 返回当前计划状态。API 仍使用现有主人认证与配置锁，不包含服务密钥或请求头。
