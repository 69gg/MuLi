# 托管启动与现有运行时接线

本文件记录尚在整合的 V2 启动路径，不代表公开 A/B 管理入口已完成。真实服务切换与用户本机运行尚未验证。

Runtime 接受真实 `ManagedBootPermit` 时，只接收该许可持有的 ConfigFile，随后由许可使用 `Store.open_existing` 打开业务数据库。它不走新库创建或迁移工厂；配置、Store 与完整格式准入完成后才构造业务组件和执行恢复。构造失败先关闭 Store，再交还 writer lease；关闭失败时继续保留所有权。

Maintenance 继续使用原任务所有权、暂停闸门、nonce 和单份激活任务，显式分派 V1/V2。V2 每次健康请求先认证 boot/nonce，再由实际 Store 和安装验证器确认当前角色，返回安装、配置、selector、unit、主身份和格式摘要。origin 只能报告原进程状态；候选或回退角色必须等持久决定后才启动外部组件。HTTP 等待被取消不会产生第二个激活任务，失败仍保持暂停。新旧协议复用同一请求路由和资源关闭流程。

CLI 从同一个 state.json 发现 managed 状态。未决事务拒绝普通命令，诊断与固定控制安装的恢复入口仍可用。已决普通命令交给所选安装，子进程核对自身解释器与包路径，避免无限委派或混用安装；固定配置和数据路径不能被覆盖。普通 service install 不能覆盖托管 unit。state 缺失但 selector 仍存在（包括悬空链接）时拒绝普通启动与命令；未发布 selector 的准备前缀不被误判为已迁入。

管理宿主使用同一份 journal 分派 V1/V2 恢复。V2 只调用固定 controller 的受限 helper，不在应用进程里直接操作服务。已决结果经真实 Store 的精确 generation/revision/instance 回执确认后，才释放配置修改；此后普通热配置不再受历史快照永久限制，旧 nonce 的健康查询仍须核对实际文件。最终 helper 提示丢失时，已认证普通 API 或新的管理请求会幂等投影结果并唤醒配置等待者。静态资源、未认证请求、尚未验证签名的 webhook 不触发该补偿，内部路由只在 nonce 验证成功后处理。

首轮新增 CLI/运行时测试与既有 Maintenance、API、组件回归合计 72 项通过（3.75 秒、峰值 144.9 MiB、swap 0），六源码 mypy 通过，Ruff 与格式检查通过。测试只用临时数据库和文件、假安装身份及取消/失败注入；没有模型、远端账户或真实用户服务。首次组合检查因测试等待条件未到达被 30 秒守卫终止，已补有界等待并修正跨模块文件系统与数据库文件名夹具；没有提高资源或时间上限。

后续配置回执接线回归 74 项通过（3.95 秒、146.4 MiB），旧 CLI/HTTP/管理宿主组 72 项通过；最终 CLI/运行时定向 24 项通过（2.69 秒、83.3 MiB），另有已认证 API 补偿与未认证/静态无副作用用例通过（0.41 秒、82.1 MiB）。九源码 mypy 通过（194.6 MiB），全部检查 swap 0、单次 30 秒限制。修正了旧 bootstrap 测试替身遗漏的新可选参数，以及 fixture 别名被自动清理的问题；没有为通过测试放宽产品验证。公开准备入口、本地候选切换和临时真实进程整体验收仍待后续闭环，不将这些接线测试视为完整 A/B 发布验收。
