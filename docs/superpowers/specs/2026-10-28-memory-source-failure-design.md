# 收藏资料整理失败提醒

明确收藏资料后，后台提炼或 embedding 最终失败目前只能从来源目录发现。此次把“原文已保存，整理失败”交给原有 Attention，在空闲时说明，主人可用现有来源目录与逐份重试继续处理。

## 范围与身份

仅原 memory_jobs 作业真正进入 failed 时生成证明；retry、日常聊天、队友报告、索引重建、取消和旧管线均不新报。来源必须通过原 attachment_source/restore_attachment_source 身份门：准确附件 ID、role、principal、空 session、不受信任、完整有界正文、附件摘要或文档提取版本，以及与注册时相同算法的来源 digest。只具备 attachment 前缀不能取得资格。不重新打开附件、不提取文档、不访问服务核查来源。

## 持久性与失效

复用 memory.pipeline.updated，事件只增加有界终态 source_failure 及宿主 occurrence ID。原作业 failed 状态先持久化；失败证明作为原 checkpoint 的独立键，与该事件同事务提交，事务内没有 await。通知过大、来源不可核、回调或事件写入失败时，不改变原失败状态和成功前缀。无新表、数据库格式门、后台任务或专用配置。

每个真实失败期生成一个随机 occurrence，既有 attention_receipt 按该逻辑身份去重。明确接纳重试时只移除失败证明并复用原 checkpoint；新的终态失败可生成新 occurrence。正常重开和重配保留原失败期，不重造事件。来源遗忘、版本变化、恢复或重试会使旧证明失效。

Attention 初读与 configuration_lock 等待后的 admission guard 都核对当前来源、作业和完整附件身份。每份来源独立成批，宿主 ingress 只附一份有界证明；Store.claim_inputs 的原目的地键纳入完整证明身份，同路由的不同失败仍分别领取，普通输入使用空值保留原合并合同。Runtime 在原 max_pending_runs 窗口内领取前再次核查，只撤销对应旧输入。上下文、模型容量等待与流式输出边界继续检查有限版本/状态元数据，失效时结束该次解释，不启动新的故障提醒。已经显示的文字不承诺撤回。

旧提醒结束后如已领取新的主人输入，先按原触发输入规则建立新请求，再核验新请求，避免旧证明失效使已送达的新输入无人处理。只有队友报告时仍继承旧证明，并在进入上下文之前核验；不把已送达消息盲目重新排队。

## 用户行为

新增 attention.events 的 memory 选项，新配置默认开启；保留已有配置明确列表的含义。复用 attention.enabled、默认独立目的地、只读工具与显式渠道发送边界。证明和说明只含固定码、准确来源、版本和失败时间，不含正文或异常正文，不自动重试、重建、改配置或外发。

## 验证边界

独立后审发现领取新输入期间旧证明失效的 P2 路径，已调整请求归属顺序。仅撤回这两处修正的临时副本准确复现两项失败、两项正控通过；修复后的两份新增测试共 47 项通过（12.98 秒；守卫 14.266 秒、峰值 102.9 MiB、swap 0）。覆盖收藏身份、终态/重试、成功前缀、去重、配置锁、排队、模型容量等待、流式迟到输出、真实主人输入与队友报告的请求归属。

早先 collection/import 与类型检查的异常超时日志继续保留。实际原因已定位到 `/tmp` 为 tmpfs，检查结束后遗留工件仍占用共享 cgroup；当时无进程、匿名内存为零，shmem 仍约 921 MiB。只迁移本任务核验过的冻结工件到磁盘并保留旧路径后，相同 Python、依赖和原资源上限下恢复验证；没有升级环境、提高期限或删除证据。守卫现统一验证磁盘临时目录，46 项无真实服务回归和一次真实受限子进程的目录继承检查通过，见[开发验证](../../development.md)。

完整平台矩阵仍须由精确签名候选的托管 CI 验收。未验证真实账号、模型、渠道或桌面。

严格类型检查已在不改规则、依赖或 YAML 导入的前提下以 `--no-incremental` 完整通过 178 份源码（守卫 25.473 秒、峰值 450.7 MiB、swap 0）。此前增量缓存报的三项既有 `unused-ignore` 保留，不据此修改业务代码。

十三份相关测试的整合检查实收 253 项通过、一项失败（88.72 秒、峰值 299.6 MiB）。唯一失败是原配置锁竞态测试的透明包装器遗漏新增的可选参数，未进入其原业务断言；同步精确签名并转交参数后，该原用例单独通过（0.90 秒、峰值 74.9 MiB）。没有提高两秒等待或改动生产逻辑；该组合记录覆盖 254 个不同节点，不宣称一次全绿运行，也不与前述 47 项重复累计。

签名 `231467d` 的首个完整托管矩阵在 Linux/macOS 发现另一份既有系统错误来源测试的六个参数用例，其领取包装器同样未传递新增的 `discard_stale` 选项。已同步准确参数并保留原故障注入、来源判断和两秒等待；本机原文件 25 项通过（10.41 秒、峰值 103.1 MiB、swap 0）。这不代表首矩阵转为成功，修正须由下个精确签名候选完整复验。
