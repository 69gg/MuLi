# 后台渠道接收健康提醒

Telegram 与微信使用常驻后台轮询。现有失败会进入状态页并继续重试，但主助手没有对应事项；失败重试还重复持久化整个状态，成功清除错误时却不发布恢复。这会让用户无法及时知道手机入口已经不可用。

本轮沿已有系统事件、只读 Attention 与配置生命周期补齐这一条路径，不启动新轮询，不自动修改凭据、重新登录或重发消息，不把 webhook 安静误判成离线。

## 生命周期

仅两个实际轮询渠道增加接收 health。启动校验不可用记为 unavailable；后台接收或本地消息处理、游标提交失败记为 failed。固定错误码分别表明 Telegram 或微信及这两种阶段，不携带服务端错误、令牌、账号或消息正文。每个渠道每个故障期只生成一个随机 occurrence；仅一整批实际接收、逐条处理和游标提交成功才恢复，空批也有效。预检、重新调用 start 不能证明接收成功。

同步回调是尽力通知，不改变原失败重试与退避。关闭、取消和旧 manager 不得产生新通知；应用入口校验 manager 身份、配置代次、配置快照及当前任务。保存原有 notify=false，清除复制的运行和请求来源；首次持久化冻结独立默认目的地，通常为 WebUI。通知不授予操作权限。

状态页显示有限接收历史。失败期首次和真正恢复时发布 channel.updated，相同错误连续失败不再重复保存完整状态；若失败说明改变可更新状态。其它出入站状态发布、游标、私聊主人验证和 outbox 合同保持原样。关闭时 health 仅代表最近历史，不宣称当前在线。

## 验证

使用有限 Event、MockTransport、临时 Store 验证失败重复、空批恢复、新故障、启动不就绪、回调异常、取消/关闭及配置替换；核对没有令牌或错误正文进入通知。实际 Runtime 侧验证只读 Attention、忙碌延后、来源隔离、冻结路由、阈值和显式抑制。测试由主代理串行通过资源守卫执行，不连接平台、真实账号或桌面。
