# 插件故障诊断与显式恢复

## 问题与目标

用户插件是可信同进程 Python，可改工具、上下文和运行时。上下文钩子失败或超时会阻断模型请求，但清单仍只显示启动时的 loaded；手工停用缺少不运行插件代码的命令入口。不能自动吞错并继续，因为插件也可能承担用户约束。

本片保留失败阻断，补准确状态、指定插件的只读结构检查和停止服务后的显式停用/恢复。健康插件、主配置和资料保持，停用只影响下次启动；不承诺同进程代码可安全热卸载、回滚副作用或被异步超时完全隔离。

## 运行诊断

插件上下文钩子抛错或超时后，在已有 inventory 中记录插件 ID、失败阶段、异常类别和 degraded 状态，不保存异常正文、路径、消息或凭据；继续抛出原异常。后续调用仍执行原钩子，成功后可清除当前失败状态；不跳过失效约束。正常取消不当作插件故障。管理认证与原工具权限不变。

## 独立命令

`MuLi plugins inspect <id>` 只读指定插件的清单与入口结构，不导入或执行其代码，也不构造 Runtime、打开业务 SQLite 或启动服务。结果区分配置启停与结构可用，不声称插件运行健康。复用现有插件 ID、路径、清单版本和源字节限制。

`MuLi plugins disable <id>` 与 `enable <id>` 仅修改 plugins.disabled，保留其它条目和设置，不直接启动/停止服务或修改插件源码。变更入口先核查 Linux 服务停止、当前安装/配置/数据路径和已解决的维护状态，再取得既有 journal 控制锁与 writer lease；活动服务、未完成恢复、错路径和竞争写入都拒绝。配置使用现有 ConfigurationFile 的预期摘要、原子替换和目录同步，不新造写入协议。已处于请求状态时幂等，只读确认。

托管命令沿原 selected-slot 路由，不能绕过选槽或未解决事务。配置更改不写业务资料；支持的已收口托管状态按现有投影证明核验。不能证明安全时明确拒绝，不退回直接写文件。首期变更限 Linux；其它平台仍可只读检查，后续补各自停止证明，不宣称已适配。

## 验证

临时配置/插件/Store、离线 ASGI 和服务替身证明：坏 hook 状态准确且继续阻断，取消不误报，恢复成功清状态；inspect 不执行恶意标记入口；显式停用持久化后重建应用只停用目标，健康插件和配置保留。变更覆盖活动 writer、未完成事务、托管路径与投影不符、配置竞争/符号链接、幂等与拒绝后文件字节不变。CLI 参数和托管路由同样验证，不操作真实服务、桌面或用户资料。
