# 把资料交给队友

主人在网页上传资料，或从已绑定的移动渠道发送文件、语音后，MuLi 可显式选择队友并交付附件引用。派工时在 `spawn_agent` 中传 `attachment_ids`；补充时在 `send_message` 或 `send_input` 中传同一个字段。示例：

```json
{"task_name":"资料整理","prompt":"阅读这份材料并列出依据","attachment_ids":["0123456789abcdef0123456789abcdef"]}
```

给已有队友补充：

```json
{"target":"队友ID","message":"把这份补充也纳入分析","attachment_ids":["fedcba9876543210fedcba9876543210"],"wake":false}
```

`wake=false` 只放入持久邮箱；正在运行的队友在既有安全边界取得补充，不中断当前流式响应或工具。队友恢复时沿用原身份与邮箱。省略字段或传空列表保留旧调用；不隐式继承父会话或其它队友的全部资料。子队友继续派工也使用同一显式字段。

每次最多 32 个不同的本地附件 ID，按传入顺序保存。ID 必须为小写 32 位十六进制字符串，且当前元数据和普通文件均存在；目录、符号链接、缺失文件、未知 ID、重复项或非法列表使整次交接失败。校验不读正文、不复制文件、不调用转写或视觉。引用和文本同一事务入队；派工身份也在该事务保存，不产生部分交接。

队友下一轮得到有限的附件目录，包含 ID、名称、MIME 和大小；文件名是资料。正文仍需显式调用 `attachment_read`，图片用 `image_describe`，音频用 `audio_transcribe`。长转写用返回的 `transcript_id`、`revision` 和字节游标调用 `audio_transcript_read` 续读，无需重新转写。超过近期目录窗口后，可用既有 `conversation_read` 按原消息序号找回结构化引用，参见[历史证据](history-evidence.md)。

交接只表示引用已接纳，不保证文件之后仍存在、未改变，或模型已阅读。附件库沿用现有实例全局读取规则，没有新增父链 ACL；未收到引用的队友不会默认获得这条消息或目录，但这不构成按队友隔离的文件权限。模型工具仍经过既有逐次权限门、任务暂停与维护准入。

普通队内消息保留 `team:<发送会话>` 来源与 `agent:<发送会话>` 身份，不能因为资料由主人上传就变成新的主人授权。派工冻结原任务汇报来源；后续移动渠道补充不改该目的地。文件内容、文件名、转写和视觉解释均不能选择新的外发目标。新 Team/Web 本地附件入口使用严格 ID 规则；通用持久消息信封及历史仍兼容原先的有限字符串引用。

## 主人明确索取队友成果文件

队友可用真实 `fs_write` 和 `file_publish` 生成本地附件，并在原完成报告中交回实际附件引用。主人随后在私聊明确索取时，主助手可用新的 `channel_reply_files(attachment_ids, idempotency_key)` 按本轮真实私聊来源发送，Web 仍保留附件下载；不需要模型重填渠道或收件人。通用 `channel_send` 的既有文件发送能力保持。

此入口保留 external 审批与任务控制，只接纳当前主助手的真实工具执行；来源不是最近联系人或队友任意声称的目的地，Web、无来源及群聊不会回退到某个私聊。文件元数据及宿主复制证明不等于验收通过。排队不冒称送达，unknown 既不自动重发，也不能判断平台是否已收到文件。两条正式旅程与五项独立接纳负控已本地通过，包括真实超时后正常重开、原信封重投不新增运行或出站；真实账号和自然模型效果未验，见[方案](channel-reply-files-proposal.md)。

## 执行中的阶段资料与澄清（v2.52）

直接由主 MuLi 派出的队友，可在真实执行中用原 `send_input` 向自己的固定主会话ID交阶段资料、附件引用或澄清问题。主助手在安全边界协调回复，沿该队友派工时保存的原来源发送，Web同时可见；另一私聊的在途消息不应抢走这条回复。它不是队友直接向渠道发消息，也不等待队友结束后才伪装成阶段报告。

该入口沿用 `target`、`message`、`attachment_ids` 和 `wake`，附件仍先全部验证再与正文入队。仅这个真实工具调用可产生 `team-progress:<队友ID>` 来源，身份仍为队友资料；暂停、停止、维护关闭、执行代次变化或邮箱已满均不接纳。`wake=false` 不主动启动主助手，但已在运行的主助手仍可在原安全边界消费。普通 `send_message`、应用内部 `TeamManager.send` 和下述认证HTTP接口的目标范围保持不变，不能用它们给任意主会话投递。

等待主人回答时，队友可以自然结束这一轮；之后主人明确补充，主助手再用原 `send_input` 唤醒同一持久队友。v2.52两条真实离线旅程已分别验证执行中的协调与正常关闭重开后的同队友续作，旧unknown投递不自动重发；远端CI、正式发行和构件核对已闭合，真实账号与自然模型效果未验。接纳和测试边界见[阶段协作方案](team-progress-proposal.md)，发行证据见[审查记录](review-v2.52.md#发行闭合)。

认证宿主可调用 `POST /api/team/{agent_id}/messages`，JSON 传 `content` 和可选 `attachment_ids`。该接口沿用登录、同源、配置锁和维护限制，发送者由宿主决定；请求不能覆盖 principal、sender 或 origin。应用内部对应 `TeamManager.spawn(..., attachment_ids=None)` / `send(..., attachment_ids=None)`；轻量 Runtime 未组合 Attachments 时仍可使用不带附件的旧调用，非空本地引用明确报能力未就绪。

开发验收使用临时附件与离线固定模型/HTTP 替身。真实平台账户、音频编解码、外部送达与自然模型是否正确选择资料仍需各平台实测。
