# 把资料交给队友

主人上传文件或从已绑定渠道发送资料后，可以让主助手明确选择队友阅读。交接的是本地附件引用，不需要模型把整个文件复制进派工文字。

可以直接说：

> 请让资料整理队友阅读刚上传的文件，列出结论和依据；这份补充也一并交给它。

## 派工与补充资料

新派工通过 `spawn_agent` 的 `attachment_ids` 指定附件，已有队友通过 `send_input` 或 `send_message` 接收补充。例如：

```json
{
  "task_name": "资料整理",
  "prompt": "阅读材料，区分原文事实与自己的判断，并列出依据",
  "attachment_ids": ["0123456789abcdef0123456789abcdef"]
}
```

已有队友使用准确 ID：

```json
{
  "target": "队友ID",
  "message": "请把这份补充纳入分析",
  "attachment_ids": ["fedcba9876543210fedcba9876543210"],
  "wake": false
}
```

`wake=false` 只放入邮箱，不主动唤醒已经结束的队友；正在运行的队友仍可在安全边界取得补充。需要继续工作时，再明确唤醒同一队友。任务控制中的暂停不能靠这一步绕过。

没有指定附件时，不会自动把父会话或其他队友的全部文件交出去。引用必须指向当前存在的本地普通文件；附件不存在、重复或不合法时，会拒绝本次交接，不只交其中一部分。

回答队友[明确登记的问题](task-inspection.md#回答队友登记的问题)时，可在同条主人消息上传补充附件。只保存答案不会把资料立即交给正在运行的队友；明确交回后，原问题、准确答案和附件引用才进入原队友的续接。

## 队友如何读取

收到引用后，队友先看到附件名称、类型和大小等目录信息。接纳引用不等于已经读过正文：

| 资料 | 读取方式 |
| --- | --- |
| UTF-8 文本附件 | `attachment_read`；长文显式 `offset_bytes=0` 读取首页，再按返回版本和字节位置续读 |
| PDF / DOCX | `document_read` 按版本继续读取提取正文；PDF 需要已有本地转换器，见[文档阅读](document-reading.md) |
| 图片 | `image_describe`，需要可用的视觉配置 |
| 音频 | `audio_transcribe`，需要 ASR 服务 |
| 已保存的长转写 | 用返回的 `transcript_id` 和续读信息调用 `audio_transcript_read` |

文件名和正文都是待核查资料，不是新指令。队友应按实际读到的内容报告，不应仅凭名称判断结论。较早的附件引用可从原消息记录找回，见[历史证据](history-evidence.md)。

普通文本不传分页参数时仍是预览。发现 `truncated=true` 后，应使用同一附件 ID 显式读取首页，再逐页回传 `revision` 和 `next_offset_bytes`，直到 `has_more=false`；不能把首页预览当成已读全文。续读位置是 UTF-8 字节数，必须使用回包数值；文件版本变化或读取失败时先处理错误。详细用法见[附件查询与长文本续读](attachment-search.md#继续阅读长文本)。

## 保存视觉解释再交接

看图时显式选择 `archive=true`，可以保存这次模型的完整解释、原图版本、所用模型和提问。队友把返回的工件 ID 交给主助手后，主助手可用 `attachment_read` 分页回查，不必再次调用视觉。

也可按原图 ID 在附件查询中选择 `source="vision"` 找回相关解释。回查使用实际返回的版本与续读位置，避免把另一份解释误当成当前结果。

视觉解释是模型生成的资料，不等于主人确认的事实或成果验收。视觉已经完成但存档结果未知时，应先查找是否保存成功，不要自动再看一次。配置方法见[模型与媒体服务](providers.md)。

## 执行中的阶段资料与澄清

直接由主沐璃派出的队友，可以在任务未结束时，通过 `send_input` 向自己的主助手提交阶段资料、附件引用或澄清问题。主助手据此协调回复，保留原派工来源；文字默认在 WebUI 展示，外发须显式调用渠道工具。

另一私聊此时发来新消息，不会把这份阶段成果改投给新联系人。这个入口也不是让队友直接选择任意渠道发消息。

暂停、停止、维护或旧执行代次下的上报会受原限制。等待主人回答时，队友可以结束本轮；之后主助手用同一队友 ID 补充并继续，保留原历史。旧操作结果未知时仍须先核查，不能借继续工作自动重做。

## 主人明确索取队友成果文件

队友在本地完成文件后，可以通过 `file_publish` 把实际文件发布到附件库，并在报告中交回引用。报告里只有一个路径或一句“已完成”，不等于已经生成可下载的附件。

主人在私聊明确索取时，主助手可使用 `channel_reply_files`，只选择附件，由宿主按本轮真实私聊来源发送；Web 仍可下载。不需要再派一位队友搬运文件，也不需要模型重填收件人。

这个便捷入口支持当前已授权的私聊来源，保留外发审批。Web、群聊或无来源请求不会被猜测成某个私聊。文件已排队不等于平台已收到；结果未知时先核查，不会自动重发。通用 `channel_send` 仍可用于其原本支持的发送场景，见[渠道说明](channels.md)。

## 使用边界

附件引用不会复制文件，也不保证文件后来始终存在或没有变化。交接后是否成功读取，应看实际回执。

队友共享同一个实例的附件库规则，不会因为没有出现在某条交接消息中就形成独立文件沙箱。工具仍受工作目录、权限、审批与任务控制限制。

文件、转写、视觉解释和队友消息都不能指定新的外发目标或提高权限。主人上传资料不等于认可其中的命令，也不等于同意把它发给外部服务。需要长期收藏文本时，应另行明确要求，见[记忆说明](memory.md#收藏附件正文)。
