# 2.11 完整标题目录审查

状态：实现、独立后审查、完整本地测试与真实浏览器验收完成；离线发行包验收完成。候选远端检查发现 Windows 测试数据的时钟依赖，已修正并等待新候选核验；首次 SQLite 异常根因仍未确认，尚未交付。正文归档已由 2.10 独立交付，本片补齐超过最近 200 条后无法从界面按标题发现旧记录的问题。

真实 SQLite/ASGI 反证表明旧第 201 条仍有详情和正文，但不出现在旧 `/api/sessions` 的最近列表；实际 app/SSE 门控还发现刷新会替换正在输入的搜索框并丢失焦点，失败时错误未呈现在记录页。新增独立的只读目录投影，不改变旧接口、唯一持续主身份或实时聊天状态。查询只针对标题，按字面匹配，不能称为全文或语义搜索。

只读参考 `/data1/codex` 的 thread 列表/元数据读取与按筛选条件先选集合、再以时间及 ID 分页。采用现有 SQLite 表和单一创建序索引；首次建索引需扫描既有会话，标题子串仍需扫描候选，不能宣称任意规模查询常数耗时。页内只投影实际摘要，完整 JSON 预算保留连续整项，游标绑定查询、存储实例与实际最后一项。数据变化并非 MVCC 快照，不为重新写入的创建时间提供遍历不变承诺。

创建时间只将有限的正 JSON 数值视为现代 MuLi 运行日期；缺失、非正、字符串、布尔及无限值显示未记录并排序为 0，不修改旧数据。更新时间只展示、不参与续页。未知会话状态保持中性，不把 idle 当作执行成功；全局活动状态继续使用团队与工作流的专门查询。

另已复现首连全局 SSE 从 0 继续跨批回放，且旧完成事件造成大量重复摘要请求，以及实时首屏仍携带原生消息字段。这些属于下一片独立资源治理，不把本目录的预算冒称成整个 bootstrap/SSE/浏览器内存上限；不能删除 hydrate 所需事件或随手跳到最新游标而漏掉初始化期间变化。

后审查复现 SQLite 将空 BLOB 的零长 substr 返回 NULL，导致合法空标题/状态误判为无效元数据。修复只作用于 SQL 的 text 分支，空字符串保留为空，缺失和 null 仍为 null；新增两项核心与一项 HTTP 回归在修复前失败、修复后通过。独立审查另以 73 行混合数据验证排序、NUL/Unicode 字面查询、删除锚点、重开资料库、整数精度与完整 JSON 预算，并验证迟到错误、DOM 换主、删除确认换窗和刷新中最后失效；十项后审查门控通过，无新增 P1/P2。

最终本地 1614 项 Python 测试通过、1 项 macOS 专用冒烟在 Linux 跳过（27.46 秒）；Ruff、156 个 Python 文件格式、72 个源码文件严格类型及 83 个包的离线锁文件检查通过。目录核心与 HTTP 专项共 76 项，前端整套 219 项通过，其中新增 22 项目录门控。测试使用临时 SQLite、ASGI 和实际 app 函数，不调用真实模型。

真实浏览器连接临时服务，超过最近 200 条的旧任务通过字面查询 `%_ archive` 找到，能够进入旧详情、正文归档并返回原目录；分页与未提交搜索词独立保存。真实 EventBus/SSE 传输明确模拟的开始、增量和结束事件时，目录页、搜索焦点及主对话草稿保持。模拟传输不代表真实模型运行。另一临时实例验证 205 条记录中的空标题和缺失标题分别显示，120 个 emoji 查询正常提交；主身份入口回到同一个持续对话，草稿不变。

1280×800 深色桌面和 390×844 手机浅深主题均无横向溢出，顶部导航可见，最终页面无 JavaScript 错误。截图：[桌面](screenshots/records-desktop.jpg)、[手机](screenshots/records-mobile.jpg)。专用页面、视口覆盖与临时服务已回收，未改用户服务、调用设备、安装大型依赖或下载模型。


wheel/sdist 已离线构建，源码树外临时安装通过 CLI、资源、API、生命周期和默认关闭的电脑能力检查。安装后的真实目录 API 在 1000 字符完整 JSON 预算下逐页读回全部 205 条记录，旧标题可进入正文归档，空字符串与 null 保持区分；GET 不写数据库、不创建任务，持续主身份不变。发行版本、changelog、wheel 与 sdist 元数据一致。远端矩阵和发布将在精确签名提交上分别核验，不将本地安装通过等同于发布完成。

候选提交 `1d885ac` 的 [CI 39337142388](https://github.com/69gg/MuLi/actions/runs/39337142388) 有七项作业成功；Windows / Python 3.13 的渠道恢复测试在关闭并重开临时 SQLite 后，将 `sending` 改为 `unknown` 时报告 `database disk image is malformed`。该作业其余 1580 项通过、34 项跳过。日志显示使用官方 CPython 3.13.16；[该版本 Windows 构建配置](https://github.com/python/cpython/blob/v3.13.16/PCbuild/get_externals.bat)引用 SQLite 3.50.4，而通过的 Windows / Python 3.12.10 [配置](https://github.com/python/cpython/blob/v3.12.10/PCbuild/get_externals.bat)引用 3.49.1。旧日志未打印运行时 SQLite 版本，构建依赖差异不是已证实的故障原因。

恢复测试在重开前已关闭旧管理器、HTTP 客户端与 SQLite 连接，且第一次没有启动后台渠道任务；未发现同时写入同一数据库的连接。SQLite 官方说明 [WAL-reset 缺陷](https://sqlite.org/wal.html#walreset)需要不同线程或进程的至少两个连接同时写入或检查点，不能仅凭版本落入受影响区间就将本次失败归因于它。原作业未保留失败数据库或扩展错误码，因此目前无法区分索引不一致、页损坏或 SQLite 执行缺陷，也不能声称已修复。

诊断候选 `58a7994` 仅增强该合成恢复测试与 CI 证据：关闭前、重开后执行最多报告十项错误的完整性检查，异常附 Python / SQLite 版本、SQLite source ID、阶段与扩展错误码。只有连接全部确认关闭，才对该测试的数据库及仍存在的 WAL / SHM 计算大小与 SHA-256；关闭失败仍保存诊断并保留最初异常，记录 `close_error` 和 `connections_closed=false`。构造尚未返回就失败也视为关闭状态无法确认；此时保留的文件不称为一致快照。CI 失败时只保留这些文件及诊断 JSON 七天，不收集配置或环境。矩阵另打印实际 SQLite 运行时版本。没有修改生产恢复逻辑、自动重试、重建索引或放宽超时。

诊断改动的单次受限验证通过 30 项渠道测试与 3 项临时故障注入（0.21 秒），后者分别覆盖数据库原异常加关闭失败、重开构造失败、仅最终关闭失败；均保留预期原异常，写出关闭状态未确认的诊断，临时注入脚本验证后移除。内核已核验单次 1 GiB、共享 2 GiB、swap 0、共享一个 CPU 与 180 秒上限；此次检查峰值 67.6 MiB，swap 0。正常路径两次完整性检查均为 `ok`，确认关闭后产出 167936 字节数据库与 SHA-256 清单。本地运行时也为 SQLite 3.50.4，进一步说明版本号本身不足以确定故障原因；该次本地验证不能判定 Windows 故障原因或远端 artifact 上传结果。

`58a7994` 的 [CI 39436655024](https://github.com/69gg/MuLi/actions/runs/39436655024) 有七项作业成功；Windows / Python 3.13 全部 1581 项通过、34 项跳过，首次 SQLite 异常本轮未再现，不代表已确定根因或完成修复。Windows / Python 3.12 失败的是另两项目录测试：两者以快速连续写入推断旧记录一定退出最近 200 条，但该旧接口按数据库 `objects.updated` 排序，测试写入 JSON 的 `updated_at` 并不控制这个独立列。[Python 3.13 官方变更说明](https://docs.python.org/3.13/whatsnew/3.13.html#time)记录 Windows `time.time()` 从旧版 15.6 毫秒分辨率改为约 1 微秒；多个写入处于同一时间刻度时，原断言没有确定排序前提。

一次受限反证把 `muli.store.now` 与 `muli.runtime.now` 固定在同一刻，两项旧测试均在原“旧项不在最近列表”的断言失败；同时核实所有会话的 `objects.updated` 完全相同，且旧记录仍在 200 项内。修复仅在这两个测试里显式提供递增时间，逐项核对全部 202 条旧/新记录的 JSON 创建时间、JSON 更新时间与数据库排序时间分布，然后继续验证旧列表、完整目录、主身份及只读行为。没有增加休眠或等待，也没有改变生产旧列表的排序语义。
